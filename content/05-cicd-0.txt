= Why it hurts | PROBLEM
+ u

Many changes at once: when something breaks nobody knows which one. So releases get rarer, and larger, and worse.

**Continuous integration** builds and tests every change. **Continuous delivery** makes each one ready to release. **Continuous deployment** releases it by itself.

| Fear | Routine, with a way back |

## Building blocks
# c-pipe | Pipeline, stage, job | Beginner | The shape of every delivery system.
@@ user Developer ; gear Pipeline ; rack Production ; shield Stages
= Without it | PROBLEM
Each person releases in their own way.
= What it is | SOLUTION
A fixed path every change travels. **Stages** run in order, **jobs** inside a stage can run together.
= How it works
Typical stages: build, unit test, scan, package, deploy to test, integration test, approve, deploy.
= Real-time example | PRACTICE
A change with a failing test stops at minute two. It never reaches a person, let alone a customer.
? Jobs in one stage can... | never run | *run together | skip the code

# c-artifact | Artifact and registry | Beginner | The thing you actually ship.
@@ gear Build ; box Artifact ; server Servers ; bucket Registry
= Without it | PROBLEM
Each server builds the code itself, and each result is a little different.
= What it is | SOLUTION
An **artifact** is the result of a build: image, package, zip. A **registry** stores it by version.
= How it works
Build once, store, use the same one everywhere. Docker Hub, GHCR, Nexus, Artifactory, ECR.
= Real-time example | PRACTICE
Production fails. The team redeploys artifact 1.8.1 from the registry in two minutes; no rebuild.
? Build how often per version? | Per server | *Once | Never

# c-envs | Environments | Beginner | Places to try before customers see it.
@@ box Version ; server Staging ; rack Production ; server Test
= Without them | PROBLEM
Customers are the testers.
= What they are | SOLUTION
Separate copies of the system: development, test, staging, production.
= How it works
Same artifact, different settings and data. Staging should look as much like production as you can afford.
= Real-time example | PRACTICE
A date bug appears only with the real amount of data. Staging with a masked copy of production data shows it.
? Staging should resemble... | a laptop | *production | nothing

# c-testtypes | Types of tests | Beginner | What each test catches.
@@ user Developer ; shield Tests ; server System ; user Tester
= Without them | PROBLEM
Every change may break something, and you learn it from users.
= What they are | SOLUTION
| Test | Question |
| Unit | Does this function work? |
| Integration | Do parts work together? |
| End to end | Can a user finish the task? |
| Regression | Does the old still work? |
| Smoke | Is it alive after deploy? |
| Load | Can it carry the traffic? |
| Security | Can it be abused? |
| Acceptance | Is it what was asked? |
= How they fit
Fast ones first, on every change. Slow ones later or at night.
= Real-time example | PRACTICE
A smoke test after each deploy logs in and opens one order. It caught a missing setting in 30 seconds.
? After a deploy, first run... | load tests | *smoke tests | unit tests

# c-rollback | Rollback and roll forward | Beginner | Getting out of trouble.
@@ user On-call ; gear Rollback ; rack Production ; bucket Last good version
= Without it | PROBLEM
" a Who remembers the old settings?
A bad release, and no way back.
= What it is | SOLUTION
**Rollback** returns to the last good version. **Roll forward** releases a quick fix.
= How it works
Keep the last artifacts and make database changes that both versions can use.
= Real-time example | PRACTICE
Errors rise after a canary. The pipeline sends traffic back by itself in one minute, and the team finds the cause in calm.
? Rollback is hard when... | code changed | *the database changed in an incompatible way | it is Friday
