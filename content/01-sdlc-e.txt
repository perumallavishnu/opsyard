# team-tools | The tools a software team opens every day | Beginner | Which tool does what, and why one place for work matters.

= Work in emails | PROBLEM
+ t
" t Who is fixing the login bug?
" t I thought you were.
When tasks live in emails, chat threads and people's heads:
- the same bug is fixed twice by two people, or by nobody;
- nobody can say what is finished, what is blocked and what is next;
- when someone is ill or leaves, their knowledge leaves with them;
- the client asks "when?" and nobody can answer with facts.
= One place for work | SOLUTION
+ j
w t>j every task
A **work tracker** such as **Jira** records each piece of work as an item with: what needs doing, who does it, its current state, its priority, and the complete history of comments and changes. Everyone, including the client, sees the same picture.
= One place for knowledge
+ w
~ j>w links
**Confluence** (or another wiki) keeps longer-lived knowledge: decisions and their reasons, meeting notes, designs, how-to guides, onboarding pages.
- Jira says **what** to do and its state.
- Confluence says **why** and **how**.
Link them both ways, so a ticket points to the design page and the page lists its tickets.
= Code, design and talk
+ g c f
~ t>g code ;; g>j linked
| Tool | Used for | Connects to Jira by |
| GitHub or GitLab | Code, reviews, pipelines | The ticket key in branch and commit names |
| Figma | Screen designs and prototypes | A link in the ticket |
| Slack or Microsoft Teams | Quick conversations | Ticket links and bots |
| Jenkins or GitHub Actions | Build and deploy | Build status shown in the ticket |
| TestRail, Xray or Zephyr | Test cases and test runs | Tests linked to stories |
| Grafana, Datadog | Watching production | Alerts can open incident tickets |
= The rule that saves teams | PRACTICE
" t No ticket, no work.
Two simple team rules:
- **No ticket, no work**: anything that takes more than a few minutes gets an item, so it is visible and counted.
- **Decisions go in the ticket**: if something is decided in a call or chat, write one line in the ticket ("Agreed with Priya: refunds only within 30 days"). In three months nobody will find the chat message.
= Alternatives to Jira
Azure Boards, GitHub Projects, GitLab Issues, Linear, Trello, YouTrack and ClickUp do the same job. The ideas you learn here (items, types, workflows, boards, sprints, reports) carry over to all of them.
? Where does the reason for a design decision belong? | In chat | *Confluence, linked from the ticket | In someone's memory

# jira-why | Why Jira exists | Beginner | From a bug list to the place where projects live.
@h 2002 Bug tracker ; 2009 Agile boards ; 2017 Jira Cloud focus ; 2025 Work items
= 2002: a bug tracker | HISTORY
Atlassian, a company from Sydney, releases Jira to track software bugs and issues. The name comes from *Gojira*, the Japanese name of Godzilla, a playful nod to Bugzilla, a popular bug tracker of the time.
= Agile boards | HISTORY
The GreenHopper add-on brought boards, backlogs and sprints to Jira. It later became part of the product (Jira Software), and Jira grew from a bug list into the planning tool for agile teams.
= Cloud | HISTORY
Atlassian moved its focus to the hosted Cloud version and stopped selling new licences for the self-hosted Server edition in 2021; large companies that must host it themselves use Data Center.
= New words | HISTORY
In 2025 Jira Cloud renamed *issues* to **work items**, and *projects* are becoming **spaces**. Screens, older guides and colleagues mix both words, so you will hear both.
? What was Jira at first? | A chat tool | *A bug and issue tracker | A code editor

# jira | Jira basics: items, workflows, boards | Beginner | The building blocks of every Jira project.

= Work item
+ story
Every piece of work is a **work item** (formerly "issue"). Its main fields:
| Field | Meaning |
| Key | Unique ID: space key plus number, such as `SHOP-42` |
| Type | Epic, Story, Task, Bug, Subtask |
| Summary | One-line title |
| Description | Details, acceptance criteria, links |
| Assignee | Who is working on it now |
| Reporter | Who created it |
| Priority | How soon it should be done |
| Status | Where it is in the workflow |
| Labels, Components | Tags and product areas for filtering |
| Story points, Sprint, Fix version | Planning fields |
Every change is recorded in the item's **History**, with who and when.
= Types and hierarchy
+ epic bug
~ epic>story ;; epic>bug
| Type | Meaning | Example |
| Epic | A large goal, spanning several Sprints | Payments |
| Story | Something of value to a user | Pay by credit card |
| Task | Work with no direct user value | Upgrade the database to version 17 |
| Bug | Something does not work as it should | Refund fails with error 500 |
| Subtask | A piece of a story or task | Write the payment API |
Stories, tasks and bugs sit **under** an epic (their parent); subtasks sit under a story, task or bug. Larger companies add levels above epics, such as Initiative.
= Workflow
+ wf
~ story>wf
* wf
A **workflow** defines the **statuses** an item can have and the allowed **transitions** between them:
> To Do → In Progress → In Review → In Testing → Done
- To Do = accepted, not started
- In Progress = someone is working on it
- In Review = code is waiting for a teammate's review
- In Testing = a tester is checking it on staging
- Done = meets the Definition of Done
Admins can add rules: "only a tester may move to Done", "a pull request must be linked before In Review", "ask for a resolution when closing".
= Boards
+ board
~ wf>board
A **board** shows items as cards in columns, one column per status (or group of statuses).
- A **Scrum board** has a backlog view and Sprints, with a start and end date.
- A **Kanban board** has continuous flow and WIP limits per column; no Sprints.
A board is a **view over a saved filter**: change the filter, and different items appear. One project can have several boards, for example one per team.
= JQL: Jira Query Language
* board
JQL finds items with precise conditions, like SQL for Jira. Type it in **Filters, Advanced search**.
> project = SHOP AND status = "In Review" AND assignee = currentUser()
- project = SHOP = only the SHOP space
- status = "In Review" = quotes because of the space
- assignee = currentUser() = assigned to whoever runs the search
> type = Bug AND created >= -7d AND resolution = EMPTY ORDER BY priority DESC
- created >= -7d = created in the last 7 days
- resolution = EMPTY = not resolved yet
- ORDER BY priority DESC = highest priority first
> sprint in openSprints() AND labels = payments
- sprint in openSprints() = in any Sprint that is running now
Save a search as a **filter** to reuse it, share it, or build a board or dashboard on it.
= Reports and automation
+ rep
~ board>rep
Built-in reports include the **burndown chart**, **velocity chart**, **cumulative flow diagram** and **control chart** (a later lesson explains each).
**Automation rules** remove clicking: "when a pull request is merged, move the item to In Testing", "when all subtasks are done, move the story to Done", "every Monday, comment on items older than 14 days".
? What does a board show? | Only one sprint | *Work items matched by its filter | Every space

# jira-setup | Day 1: setting up the project | Beginner | The client meeting becomes a Jira project.
@ c user 0 0 Client
@ po user 1 0 Product owner
@ j board 2 0 Jira: SHOP
@ ad user 2 1 Jira admin

= Kick-off meeting
+ c po
" c A shoe shop, live in June.
" po I will write down the goals.
This chapter follows the shoe shop from the first lesson through Jira. At the kick-off, the client and the product owner agree on:
- the **goal**: sell shoes online, first in India;
- the **limits**: budget, launch in June, must accept cards and cash on delivery;
- the **people**: who decides, who must be asked, who will use it.
The product owner writes this on a Confluence page, which will be linked from Jira.
= Create the space
+ j ad
w po>ad please create SHOP
w ad>j create
A Jira administrator creates the space (project):
- **Template**: Scrum, because the team will work in two-week Sprints. (Kanban for a support team.)
- **Name and key**: "Shoe Shop" with key **SHOP**. The key starts every item's ID: SHOP-1, SHOP-2…, so choose something short and clear; it is hard to change later.
- **Access**: who may see the space, who may create and edit items.
= Configure only what you need
: j ok ready
" ad Workflow: five statuses.
The team agrees on:
| Setting | Choice for SHOP |
| Item types | Epic, Story, Task, Bug, Subtask |
| Workflow | To Do, In Progress, In Review, In Testing, Done |
| Priorities | Highest, High, Medium, Low |
| Components | web, api, payments, admin |
| Definition of Done | Reviewed, tests pass, deployed to staging, tested against criteria |
Keep it small. Every extra required field is one more thing people fill in badly or skip.
= Invite the team and connect tools
+ t
~ t>j join
Add the team with roles: **administrator** (configures the space), **member** (creates and works on items), **viewer** (reads, such as the client).
Install the **GitHub for Jira** app (or GitLab, Bitbucket). From then on, branches, commits, pull requests and builds that mention a key such as SHOP-42 appear in that item automatically.
= First epics
w po>j 5 epics
The product owner turns the goals into a first set of epics, the big chunks of the product:
| Key | Epic | Contains, for example |
| SHOP-1 | Catalogue | Browse, search, product page |
| SHOP-2 | Account | Sign up, log in, addresses |
| SHOP-3 | Cart | Add, remove, change size |
| SHOP-4 | Payments | Card, cash on delivery, refunds |
| SHOP-5 | Orders and returns | Order history, tracking, returns |
Stories will be written under each epic over the next days.

# jira-backlog | Day 2: writing a ready ticket | Beginner | From a wish to a ticket a developer can start.
@ c user 0 0 Client
@ ba user 1 0 Business analyst
@ t card 2 0 SHOP-42
@ dev team 2 1 Dev team
@ qa user 1 1 Tester
= A bad ticket | PROBLEM
+ c t
w !c>t "payment broken"
: t err unclear
> Summary: payment broken
Nobody can start on this. Which page? Which payment method? What happened, and what should have happened? The developer must chase the reporter, who has forgotten the details. Unclear tickets are the most common cause of wasted work.
= A good story | SOLUTION
+ ba
w ba>t rewrite
: t ok clear
The business analyst rewrites the wish as a story a developer can start and a tester can check:
> Summary: Pay by credit card
> As a buyer I want to pay by card so that I get my shoes at once.
> Acceptance criteria:
>   Given a valid card, when I pay, then I see an order number and get an email.
>   Given a refused card, then I see the bank's reason and my cart is kept.
>   Given 3-D Secure is required, then I am sent to my bank and back.
> Design: link to Figma   Epic: SHOP-4   Component: payments
- Summary = short and specific; it appears on the board card
- As a… I want… so that… = who, what and why
- Acceptance criteria = the checks that decide when it is done
- Design / Epic / Component = links and fields for context and filtering
= A good bug report
* t
> Summary: Refund of a cancelled order fails with error 500
> Steps to reproduce: 1 log in as test buyer  2 open order 1009  3 press Refund
> Expected: "Refund confirmed" message
> Actual: error page, HTTP 500
> Environment: staging, Chrome 131, build 214
> Attachments: screenshot, server log extract
- Steps to reproduce = exact actions, so anyone can see the bug happen
- Expected / Actual = what should happen versus what does
- Environment = where, which browser, which build
- Attachments = evidence that saves time
**Severity** is how bad the damage is; **priority** is how soon to fix it. A spelling mistake in the company name on the home page is low severity but high priority; a crash in a rarely used admin report may be high severity but lower priority.
= Refinement
+ dev qa
" dev What about 3-D Secure?
" qa I will test an expired card.
w qa>t test ideas
Once a week the team meets for **backlog refinement**: they read the upcoming tickets together, ask questions, find missing cases, split stories that are too big, and estimate. Testers add test ideas early ("expired card", "card from another country"), which often reveals missing acceptance criteria before any code is written.
= Estimating
" dev Five points.
" dev Eight, the bank API is new.
In **planning poker** everyone chooses a card (1, 2, 3, 5, 8, 13) in secret, then all reveal at once. The highest and lowest explain their reasoning: here, one developer knows the bank's test API is new and badly documented. After a short discussion the team agrees on 8 and writes it in the **Story points** field.
= Definition of Ready | PRACTICE
* t
Before a story goes into a Sprint, the team checks it is **ready**:
- the value is clear (who and why);
- acceptance criteria are written;
- designs are linked;
- dependencies are known (another team, a bank test account);
- it is estimated and small enough to finish in one Sprint.
? Severity means... | how soon to fix | *how bad the damage is | who reported it

# jira-sprint | Days 3 to 12: a Sprint on the board | Beginner | Planning, the daily board, blockers and the burndown.
@ po user 0 0 Product owner
@ b board 1 0 Sprint board
@ dev user 2 0 Developer
@ qa user 2 1 Tester
@ sm user 0 1 Scrum master
@ g gauge 1 1 Burndown
= Sprint Planning in Jira
+ po b
" po Goal: a buyer can pay by card.
w po>b top stories
In the **Backlog** view, the team drags stories from the top of the backlog into the Sprint section. Jira adds up their story points; the team stops near its recent **velocity** (for example 30 points), minus holidays.
The product owner types the **Sprint Goal** ("A buyer can pay by card"), chooses the dates (two weeks), and presses **Start sprint**. The items now appear on the Sprint board.
= Pick up work
+ dev
" dev I take SHOP-42.
~ b>dev In Progress
A developer **assigns** the item to herself and drags it to **In Progress** the moment she starts. She creates her branch from the ticket's development panel so the key is in its name.
The board must always tell the truth: an item in To Do that someone is secretly working on hides information from the team.
= Daily Scrum at the board
+ sm
" dev Bank test account is missing.
: b warn SHOP-42 blocked
w sm>po get the account
The team stands in front of the board (or shares it on screen) and walks it **from right to left**: what is closest to Done, and what is needed to finish it?
A blocked item is **flagged** (it turns yellow) with a comment saying why: "waiting for bank test account". The Scrum Master takes the problem away to solve it with the product owner.
= Review and test
+ qa
w dev>b In Review
~ b>qa In Testing
" qa Expired card passes.
When the code is ready, the developer opens a pull request and moves the item to **In Review**. A teammate reviews it. After merge, the build is deployed to staging and the item moves to **In Testing**.
The tester checks every acceptance criterion and the test ideas. "Expired card is accepted" is a defect: either a bug item linked to the story, or the story goes back to In Progress with a comment, according to the team's rules.
= Watch the trend
+ g
~ b>g
: g warn flat for 3 days
On day 6, the **burndown chart** has been flat for three days: five items are In Progress, none finished. The team agrees to **stop starting and start finishing**: two developers help review and test the oldest items instead of picking up new ones. The line starts falling again.
= End of the Sprint
* po b
" po 4 of 5 stories done.
On the last day:
- **Sprint Review**: the team demonstrates the four finished stories on staging to the client;
- **Retrospective**: what to improve (here: request test accounts during refinement, not mid-Sprint);
- **Complete sprint** in Jira: the unfinished story moves back to the backlog or into the next Sprint. Unfinished work does not count "half"; only Done stories add to velocity.
? When do you move a ticket to In Progress? | At the end of the day | *When you start it | When it is done

# jira-dev | One ticket from request to production | Intermediate | Jira, Git, CI and deployment joined by one key.
@ j card 0 0 SHOP-42
@ d user 1 0 Developer
@ g db 2 0 GitHub
@ ci gear 3 0 CI pipeline
@ q user 3 1 Tester
@ p rack 2 1 Production
@ s user 1 1 Support
= Branch with the key
+ j d g
~ j>d assigned
w d>g branch
$ git switch -c SHOP-42-pay-by-card
- switch -c = create and switch to a new branch
- SHOP-42-pay-by-card = the ticket key first, then a short description
$ git commit -m "SHOP-42 Add card payment form"
- SHOP-42 at the start of the message = links this commit to the ticket
With the GitHub for Jira app installed, any branch, commit or pull request that contains the key appears in that ticket automatically.
= Pull request
~ g>j shows in the ticket
* j g
$ git push -u origin SHOP-42-pay-by-card
- push -u origin … = upload the branch and remember where it is pushed
The developer opens a pull request titled "SHOP-42 Pay by credit card". The ticket's **Development** panel now shows: 1 branch, 4 commits, 1 pull request (open). Nobody needs to ask "is it merged yet?"; they can see it.
= Build and test automatically
+ ci
~ g>ci build ;; ci>j passed
The CI pipeline builds and tests the pull request, and its result (passed or failed) is shown in the ticket too. A Jira **automation rule** can move the ticket:
> When: pull request merged   Then: transition work item to "In Testing"
- When = the trigger, coming from GitHub
- Then = the action in Jira
= Verify on staging
+ q
~ ci>q staging
" q All criteria met.
: j ok Done
After the merge, the pipeline deploys to staging. The tester opens the staging site, walks through each acceptance criterion, and records the result in the ticket (or in a linked test run in Xray or Zephyr). All pass, so the ticket moves to **Done**.
= Release with a version
+ p
~ ci>p version 1.4
A Jira **version** (release), such as `1.4`, groups the items that ship together; each item's **Fix version** field says which release contains it.
- The **Releases** page shows progress: 18 of 20 items done.
- Pressing **Release** marks the version as shipped, and Jira can generate **release notes** from the item summaries.
- Anyone can see which features and fixes are in production.
= After release, the loop starts again
+ s
" s A buyer cannot pay from Norway.
w s>j new bug linked
A week later, Support hears that buyers with Norwegian cards cannot pay. They open a bug, **link** it to SHOP-42 ("is caused by"), and the developer who picks it up sees the whole history: the original story, its discussion, the code, the tests and the release.

# jira-bug | The life of a bug | Beginner | Every status a defect passes through.
@ q user 0 0 Tester
@ n card 1 0 New
@ t user 2 0 Team lead
@ d user 3 0 Developer
@ f shield 3 1 Fixed
@ c flag 2 1 Closed
@ r card 1 1 Reopened
= Found and reported
+ q n
" q Refund gives error 500.
w q>n report
A tester (or user, or monitoring alert) finds a defect. Before creating a new bug, search for an existing one:
> type = Bug AND text ~ "refund" AND resolution = EMPTY
- text ~ "refund" = items whose summary, description or comments contain "refund"
If none exists, report it with steps, expected and actual result, environment and evidence. Its status is **New** (or To Do).
= Triage
+ t
~ n>t review
" t Real, critical, fix today.
In **triage**, a lead or the product owner looks at new bugs, usually daily:
- Is it real? Can it be reproduced?
- How severe is it, and how soon must it be fixed (priority)?
- Who should fix it, and in which Sprint?
Other outcomes are recorded as a **resolution**: **Duplicate** (linked to the original), **Cannot reproduce** (with what was tried), **Won't do** / **Not a bug** (works as designed), or **Deferred** to a later release.
= Fix
+ d
w t>d assign
" d A missing null check.
The developer moves the bug to In Progress, **reproduces** it first, then writes an automated test that **fails** because of the bug. Then they fix the code until the test passes, and open a pull request with the key, such as "SHOP-87 Handle refund of cancelled order". The new test stays forever, so this bug cannot quietly return.
= Retest
+ f
~ d>f build 215 ;; f>q retest
When the fix is deployed (build 215), the bug goes back to the tester. They repeat **exactly** the original steps on that build, then also check nearby features (**regression testing**): refunds of normal orders, partial refunds.
= Closed or reopened
+ c r
~ f>c works ;; !f>r still fails
- Retest passes: the tester sets the bug to **Done** / **Closed** with resolution **Fixed**, noting the build number.
- Retest fails: it is **Reopened** with new evidence ("still fails for orders paid by wallet"), and goes back to the developer.
A bug is closed by the person who verified it, not by the person who fixed it.
= Learn from it | PRACTICE
" t Why did no test catch this?
Track **where** bugs are found: in development, in testing, on staging, or by users in production. Each bug found by a user means a test was missing; add it. Over time, a rising share found early shows the team's quality is improving.
> type = Bug AND created >= startOfMonth() AND "Found in" = Production
- "Found in" = a custom field the team added for this purpose
- startOfMonth() = since the first day of this month
? Who usually closes a bug? | The client | *The tester after a successful retest | Anyone

# jira-reports | Reports, dashboards and honest numbers | Intermediate | What each Jira report tells you, and what it does not.
@ b board 0 0 Board
@ bd gauge 1 0 Burndown
@ v gauge 2 0 Velocity
@ cf gauge 1 1 Cumulative flow
@ m user 2 1 Manager
= Burndown chart
+ b bd
~ b>bd
The **burndown** shows work remaining (story points) for each day of **one Sprint**, with a grey ideal line falling to zero.
| Shape | Usually means |
| Follows the ideal line | Healthy |
| Flat for several days | Items started but not finished |
| Steps up | Scope added during the Sprint |
| Drops only on the last day | Items are finished in a rush, or the board is updated late |
= Velocity chart
+ v
~ bd>v
**Velocity** is the number of story points **completed** per Sprint, shown as bars for recent Sprints, with "committed" beside "completed". Plan the next Sprint from the **average of the last three**, not the best one.
!! Never compare teams by velocity, and never set it as a target. Points mean different things in each team, and people will simply start giving bigger estimates.
= Cumulative flow diagram
+ cf
~ b>cf
The **cumulative flow diagram** (CFD) shows, over weeks, how many items were in each status, as coloured bands stacked on top of each other.
- Bands of steady width: work flows smoothly.
- A band that **grows wider**, such as "In Testing", is a **bottleneck**: work arrives faster than it leaves.
- The horizontal distance across the bands is roughly the cycle time.
= Control chart
* b
The **control chart** plots the **cycle time** of each finished item: how long it took from In Progress to Done. It shows the average and the spread, and answers "how long does a ticket usually take?" Dots far above the rest are worth a conversation: what made them slow?
= Dashboards and honest forecasts
+ m
~ v>m ;; cf>m
" m When will payments be ready?
A **dashboard** combines gadgets (filter results, charts, Sprint health) on one page for managers and clients.
When asked "when will it be ready?", answer with a **range based on data**: "18 stories, about 45 points, remain in the Payments epic. Our velocity has been 25 to 32. So two Sprints at best, more likely two to three." That is honest, and it updates as the team learns.
? A widening "In Testing" band means... | testers are fast | *a bottleneck in testing | the Sprint ended
