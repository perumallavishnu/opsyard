## Parts of GitHub
# c-ghrepo | Repository page and README | Beginner | The front door of a project.
@@ user Visitor ; doc README ; db Code ; shield Licence
= Without it | PROBLEM
" a How do I start this?
A stranger finds your code. Without explanation they cannot tell what it does, how to run it, whether it is maintained, or whether they are even allowed to use it. Most leave within a minute.
= What it is | SOLUTION
Every repository on GitHub has a web page at `github.com/owner/name`. Besides the code it shows a few special files, each with its own job:
| File | Answers |
| `README.md` | What is this, how do I run it, how do I use it? |
| `LICENSE` | Am I allowed to use, change and share it? |
| `CONTRIBUTING.md` | How do I help, and what do you expect? |
| `SECURITY.md` | How do I report a vulnerability privately? |
| `.gitignore` | Which files are never committed |
The **About** box on the right adds a one-line description, a website link and **topics** (tags that help people find the project).
= Create a repository
On github.com: **+** (top right), **New repository**, choose a name, public or private, and create. Then connect your local project:
$ git remote add origin https://github.com/ana/shop.git
$ git push -u origin main
- remote add origin = remember GitHub's address under the name `origin`
- push -u origin main = upload `main` and link it for later pushes
With the GitHub CLI (`gh`) you can do it all from the terminal:
$ gh repo create shop --public --source=. --push
- gh repo create shop = create a repository named `shop` on your account
- --public = visible to everyone (`--private` for invited people only)
- --source=. = use the current folder as its content
- --push = push the local commits straight away
= Public, private and roles
- **Public:** anyone can read and clone; only people you add can change it.
- **Private:** only invited people can see it.
People you invite get a **role**:
| Role | Can |
| Read | View and clone, open issues |
| Triage | Manage issues and pull requests, no code changes |
| Write | Push to branches, merge pull requests |
| Maintain | Manage the repository without the most dangerous settings |
| Admin | Everything, including deleting the repository |
Give people the lowest role that lets them do their job.
= Write a useful README
A good README answers, in order:
- one or two sentences: what it is and who it is for;
- a screenshot or short example;
- how to install and run it, with exact commands;
- how to contribute, and the licence.
Markdown (`.md`) is plain text with light formatting: `#` for headings, `**bold**`, backticks for `code`, `-` for lists. GitHub turns it into a formatted page.
= Real-time example | PRACTICE
A small company publishes an internal library as open source. The first version has only code; nobody uses it. They add a README with a two-minute quick start, an MIT licence and a CONTRIBUTING guide. Within six months 200 projects use it and outsiders have fixed 15 bugs.

# c-issues | Issues and Projects | Beginner | Work lists beside the code.
@@ user User ; card Issue ; team Dev team ; board Project
= Without them | PROBLEM
Bug reports arrive by chat, email and in the corridor. Nobody writes them down, two people fix the same thing, and the important report from last month is forgotten.
= What they are | SOLUTION
An **issue** is one tracked piece of work or discussion: a bug, a feature idea, a question. Each has a number (`#42`), a title, a description, comments and a state: open or closed.
A **Project** is a board or table that collects issues and pull requests, with columns such as To do, In progress and Done, plus custom fields like priority or estimate.
= Organise issues
- **Labels** group issues: `bug`, `enhancement`, `good first issue`.
- **Assignees** say who is working on it.
- **Milestones** group issues for a release or date.
- **Issue templates** (in `.github/ISSUE_TEMPLATE/`) ask reporters for steps, expected and actual result.
$ gh issue create --title "Refund fails for zero amount" --label bug
- gh issue create = open a new issue from the terminal
- --title "…" = the issue's title
- --label bug = attach a label
$ gh issue list --assignee @me
- --assignee @me = only issues assigned to you
= Link issues and code
Write a keyword and the issue number in a pull request description:
> Closes #42
- Closes #42 = when this pull request is merged into the default branch, issue 42 is closed automatically. `Fixes` and `Resolves` work too
- #42 (alone) = only a link, it does not close anything
Anyone reading the issue later sees which change fixed it.
= Real-time example | PRACTICE
A five-person start-up plans everything in GitHub Projects: each week they drag issues into "This sprint". A 200-person company uses Jira for planning across many teams and connects it to GitHub, so a Jira ticket shows the pull requests and commits that belong to it.
? What closes an issue on merge? | A label | *The word Closes with its number | A star

# c-fork | Fork, star, watch | Beginner | Taking part in someone else's project.
@@ user You ; db Your fork ; db Their project ; user Maintainer
= Without it | PROBLEM
You found a bug in an open-source tool and know how to fix it, but you have no permission to push to its repository. And the maintainers cannot give write access to every stranger.
= What it is | SOLUTION
A **fork** is your own copy of someone else's repository, on GitHub, under your account. You can change it freely, then offer the change back with a **pull request**. The maintainers decide whether to accept it.
The original repository is usually called **upstream**.
- **Star** = a public bookmark; also shows the project is popular.
- **Watch** = get notifications about activity.
= Contribute step by step
1. Click **Fork** on the project page. Then:
$ git clone https://github.com/ana/tool.git
- ana/tool = **your** fork, not the original
$ git remote add upstream https://github.com/original/tool.git
- remote add upstream = also remember the original, to get its future changes
$ git switch -c fix-typo
$ git commit -am "Fix typo in install guide"
- -a = stage all changes to tracked files before committing; -m = message
$ git push -u origin fix-typo
- origin = your fork (you may push there)
2. On GitHub, click **Compare & pull request** to propose the branch to upstream.
= Keep your fork up to date
$ git fetch upstream
$ git switch main
$ git merge upstream/main
- fetch upstream = download the original's new commits
- merge upstream/main = bring them into your `main`
The **Sync fork** button on GitHub does the same.
$ gh repo fork original/tool --clone
- gh repo fork --clone = fork and clone in one step, with `upstream` already set up
= Real-time example | PRACTICE
A student notices a wrong command in a popular tool's documentation. She forks it, fixes one line, and opens a pull request. The maintainer merges it the next day. Ten minutes of work, and her name is now in the project's contributors.
? Contribute without write access by... | email | *fork and pull request | star

# c-runner | Workflow, job, step, runner | Beginner | The words of GitHub Actions.
@@ flag Event ; doc Workflow ; server Runner ; card Steps
= Without them | PROBLEM
Tests run only when someone remembers. A broken change reaches `main`, and the next person to pull spends the morning finding out why nothing works.
= What they are | SOLUTION
**GitHub Actions** runs commands automatically when something happens in a repository. Five words describe it:
| Word | Meaning | Example |
| Event | What starts it | A push, a pull request, a schedule |
| Workflow | A YAML file describing the automation | `.github/workflows/ci.yml` |
| Job | A group of steps that run on one machine | `test` |
| Step | One command or one ready-made action | `npm test` |
| Runner | The machine that runs a job | `ubuntu-latest`, provided by GitHub |
= A first workflow
> name: CI
> on: [push, pull_request]
> jobs:
>   test:
>     runs-on: ubuntu-latest
>     steps:
>       - uses: actions/checkout@v4
>       - run: npm ci
>       - run: npm test
- name = the label shown in the Actions tab
- on = the events that start it: every push and every pull request
- jobs = the jobs; `test` is just a name you choose
- runs-on = the kind of runner
- uses = run a published action; `actions/checkout` downloads your repository onto the runner
- run = a shell command
= How jobs relate
- Jobs run **in parallel** by default, each on its own fresh machine.
- `needs: test` makes a job wait for another and run only if it passed.
- A **matrix** runs the same job for several values, such as three Node versions.
- If any step fails (exit code not 0), the job turns red and later steps are skipped.
= Watch it from the terminal
$ gh run list
- gh run list = recent workflow runs and their status
$ gh run watch
- gh run watch = follow the current run live until it finishes
= Real-time example | PRACTICE
A team adds the workflow above. Every push now lints, tests on Node 22 and 24, and builds, in about six minutes. A pull request that breaks a test shows a red cross before anyone reviews it, so broken code never reaches `main`.
? A job runs on a... | branch | *runner | label

# c-ghsecret | Secrets, variables, environments | Intermediate | Settings for automation.
@@ user Admin ; key Secret ; gear Workflow ; gate Environment
= Without them | PROBLEM
A workflow needs a token to publish a package or deploy. If the token is written in the YAML file, everyone who can read the repository can steal it, and it stays in Git history forever.
= What they are | SOLUTION
- **Secrets** are encrypted values (tokens, passwords). Workflows can use them, but nobody can read them back, and GitHub hides them in logs as `***`.
- **Variables** are plain, non-secret settings, such as a region or a URL.
- **Environments** (such as `staging`, `production`) group secrets and variables, and can require **approval** before a job uses them.
They can be set per repository, per organisation, or per environment.
= Add and use a secret
In the repository: **Settings**, **Secrets and variables**, **Actions**, **New repository secret**. Or:
$ gh secret set NPM_TOKEN
- gh secret set = create or replace a secret; it asks for the value so it never appears in your shell history
- NPM_TOKEN = the secret's name
In the workflow:
> - run: npm publish
>   env:
>     NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
- ${{ secrets.NPM_TOKEN }} = replaced by the secret's value when the job runs
- env = hand it to the command as an environment variable, not on the command line
= Environments with approval
> jobs:
>   deploy:
>     environment: production
- environment: production = this job uses the `production` environment: its secrets, and its protection rules
In **Settings, Environments, production** you can name required reviewers, add a wait timer, and allow only the `main` branch.
!! Workflows started by pull requests from forks get **no** secrets by default, because the fork's author controls that code.
= Real-time example | PRACTICE
A team's deploy job to `production` pauses with "Waiting for review". One of two named leads opens the run, checks what will be deployed, and approves. Every approval is recorded with name and time, which their auditors ask for once a year.
? Approval before production belongs to... | a label | *an environment | a fork
