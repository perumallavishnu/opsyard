# tf-flow | init, plan, apply, destroy | Beginner | The everyday cycle.
@ f doc 0 0 Config
@ p card 1 0 Plan
@ s db 1 1 State
@ a gear 2 0 Apply
@ c cloud 3 0 Cloud
= init
+ f
$ terraform init
Downloads providers and modules, sets up the backend, writes `.terraform.lock.hcl`. Commit that lock file.
= plan
+ p s
~ f>p want ;; s>p have
$ terraform plan -out=tfplan
Refreshes state from the cloud and compares it to your files.
= Read it
* p
: p warn -/+ replace
`+` create, `~` update in place, `-` destroy, `-/+` **replace**. A replaced database loses its data.
= apply
+ a c
~ p>a ;; a>c create ;; a>s record
$ terraform apply tfplan
Applies exactly that saved plan.
= destroy | RISK
~ !a>c remove
$ terraform destroy
`prevent_destroy` in `lifecycle` guards critical resources.
? What does -/+ mean? | Update in place | *Destroy and recreate | No change

## State and structure
# tf-state | State, backends and locking | Intermediate | Terraform's memory.
@ a laptop 0 0 Ana
@ b laptop 0 1 Ben
@ l key 1 1 Lock
@ s bucket 1 0 Remote state
@ c cloud 2 0 Cloud
= Why state
+ a s c
~ a>s ;; s>c maps
State links `aws_instance.web` to the real `i-0abc`. Without it Terraform would not know what it owns.
= On a laptop | PROBLEM
+ b
~ !b>c second copy
Two state files means two people fighting over the same infrastructure.
= Remote backend | SOLUTION
~ a>s ;; b>s
> terraform {
>   backend "s3" {
>     bucket = "acme-tfstate"
>     key = "prod/app.tfstate"
>     region = "eu-west-1"
>     use_lockfile = true
>   }
> }
Turn on bucket versioning.
= Locking
+ l
~ a>l held ;; !b>l wait
`use_lockfile` uses S3 itself. The older DynamoDB method is **deprecated**.
= Secrets | RISK
* s
: s warn sensitive
State may hold passwords in plain text. Encrypt and restrict it. Ephemeral values and write-only arguments, in recent versions, keep some secrets out.
= Change state safely
$ terraform state list
Use `moved`, `import` and `removed` blocks so changes are reviewed, instead of editing state by hand.
? Recommended S3 locking today? | DynamoDB | *use_lockfile | No lock

# tf-mod | Variables, outputs, modules | Intermediate | Reuse without copying.
@ v doc 0 0 Variables
@ r folder 1 0 Root module
@ n box 2 0 network module
@ d box 2 1 app module

= Variables
Typed inputs with validation, so a wrong value fails at plan time rather than in production.
+ v r
~ v>r
> variable "env" {
>   type = string
>   validation {
>     condition = contains(["dev","prod"], var.env)
>     error_message = "dev or prod"
>   }
> }
= Modules
+ n d
~ r>n ;; r>d
> module "network" {
>   source = "terraform-aws-modules/vpc/aws"
>   version = "~> 6.0"
>   cidr = "10.0.0.0/16"
> }
A module is a folder of `.tf` files with inputs and outputs. Pin versions.
= Outputs
+ o
~ n>o vpc_id ;; o>r
Values other code can read.
= for_each
* d
> for_each = toset(["a","b","c"])
Prefer `for_each` to `count`: removing the middle item of a counted list shifts the rest and may recreate them.
= Data sources
* r
`data` blocks read things Terraform does not manage, such as the newest machine image.
? Why for_each over count? | Faster | *Stable keys | Cheaper
