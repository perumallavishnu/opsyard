= Click by click | PROBLEM
" u Was that setting on or off?
+ u con c
~ u>con click ;; !con>c forgot a setting
An engineer builds the production network by clicking through the cloud console: 60 screens, hundreds of settings. A month later, staging must be built the same way. Nobody remembers every click, nobody reviewed them, and nobody knows who changed a firewall rule last Tuesday.
= Infrastructure as code | SOLUTION
+ f t
~ u>f write ;; f>t ;; t>c create
**Infrastructure as code** (IaC) means describing infrastructure in text files and letting a tool create it.
> resource "aws_s3_bucket" "logs" {
>   bucket = "acme-logs-prod"
> }
- resource = something Terraform manages
- "aws_s3_bucket" = the type; "logs" = your name for it
- bucket = the real bucket's name in AWS
The files are stored in Git: reviewed in pull requests, versioned, and reusable for another environment or account.
= Declarative
* f
You describe the **result**, not the steps. Terraform compares the files with what exists and works out what to create, change or delete, and in which order (a subnet before the server that uses it).
Change `instance_type` from `t3.small` to `t3.large` in the file, and Terraform resizes the server. Delete the block, and it deletes the server.
= Providers
* t
~ t>c API
Terraform itself knows no clouds. **Providers** translate its requests into each service's API: AWS, Azure, Google Cloud, Kubernetes, GitHub, Cloudflare and thousands more. One tool and one language for all of them.
= Terraform and OpenTofu
In 2023 HashiCorp moved Terraform to the Business Source License, which limits some commercial uses. The community created **OpenTofu**, an open-source fork under the Linux Foundation. The language and commands are largely the same: `tofu plan` instead of `terraform plan`.

# tf-flow | init, plan, apply, destroy | Beginner | The everyday cycle.
@ f doc 0 0 Config
@ p card 1 0 Plan
@ s db 1 1 State
@ a gear 2 0 Apply
@ c cloud 3 0 Cloud
= init: prepare the folder
+ f
$ terraform init
- init = download providers and modules, connect to the state backend, write `.terraform.lock.hcl`
Run it once in a new folder, and again whenever you add a provider, a module or change the backend. Commit the lock file; do not commit the `.terraform/` folder.
= plan: what would change
+ p s
~ f>p want ;; s>p have
$ terraform plan -out=tfplan
- plan = refresh what really exists, compare with your files, and list the differences
- -out=tfplan = save this exact plan to a file, to apply later
Plan changes nothing. It is safe to run any time, and it is what reviewers read.
= Read the plan
* p
: p warn -/+ replace
> # aws_instance.web will be updated in-place
>   ~ instance_type = "t3.small" -> "t3.large"
> # aws_db_instance.main must be replaced
> -/+ resource "aws_db_instance" "main" {
>       ~ engine_version = "16.4" -> "17.2" # forces replacement
> Plan: 1 to add, 1 to change, 1 to destroy.
- + = create
- ~ = update in place
- - = destroy
- -/+ = **replace**: destroy and create again; "forces replacement" names the attribute that causes it
!! A replaced database starts empty. Read every `-/+` line before applying.
= apply: make it so
+ a c
~ p>a ;; a>c create ;; a>s record
$ terraform apply tfplan
- apply tfplan = carry out exactly the saved plan, nothing more
$ terraform apply
- apply (without a plan file) = make a fresh plan, show it and ask `yes` before acting
After each change, Terraform records the result in the state.
$ terraform apply -target=aws_instance.web
- -target = limit to one resource; for emergencies only, as it can leave the rest inconsistent
= destroy | RISK
~ !a>c remove
$ terraform destroy
- destroy = delete **everything** this configuration manages, after asking for `yes`
Useful for test environments that should not cost money at night. Protect important resources:
> lifecycle { prevent_destroy = true }
- prevent_destroy = any plan that would delete this resource fails with an error
? What does -/+ mean? | Update in place | *Destroy and recreate | No change

## State and structure
# tf-state | State, backends and locking | Intermediate | Terraform's memory.
@ a laptop 0 0 Ana
@ b laptop 0 1 Ben
@ l key 1 1 Lock
@ s bucket 1 0 Remote state
@ c cloud 2 0 Cloud
= Why state
+ a s c
~ a>s ;; s>c maps
The state records that the block `aws_instance.web` is the real server `i-0abc123`. Without it, Terraform could not tell its own server from the 40 others in the account, and would create a new one on every run.
= State on a laptop | PROBLEM
+ b
~ !b>c second copy
Ana has the state file on her laptop. Ben clones the code and runs `terraform apply` with no state. Terraform thinks nothing exists and creates a second set of everything, or fails with "already exists" errors.
= Remote backend | SOLUTION
~ a>s ;; b>s
> terraform {
>   backend "s3" {
>     bucket       = "acme-tfstate"
>     key          = "prod/app.tfstate"
>     region       = "ap-south-1"
>     encrypt      = true
>     use_lockfile = true
>   }
> }
- backend "s3" = keep the state in an S3 bucket
- bucket / key = which bucket, and the path of this project's state inside it
- encrypt = true = encrypt the file at rest
- use_lockfile = true = lock with a small file in the same bucket
Turn on **versioning** for the bucket, so an older state can be restored after a mistake.
$ terraform init -migrate-state
- -migrate-state = move an existing local state into the new backend
= Locking
+ l
~ a>l held ;; !b>l wait
While Ana runs `apply`, Terraform holds a lock. If Ben starts at the same moment, he gets "Error acquiring the state lock" and waits, instead of both writing at once and corrupting the state.
`use_lockfile` locks with S3 itself. The older method with a DynamoDB table is **deprecated**.
$ terraform force-unlock 3f9a2c1b-…
- force-unlock = remove a stale lock left by a crashed run; only when you are sure nobody is running
= Secrets in state | RISK
* s
: s warn sensitive
State stores attributes in plain text, including database passwords and private keys created by Terraform. Anyone who can read the state can read them.
- Encrypt the backend and give read access to very few people and roles.
- Prefer passwords created and kept by the cloud's secret manager.
- Recent versions support **ephemeral** values and **write-only** arguments, which are never saved to state.
= Change state safely
> moved {
>   from = aws_instance.web
>   to   = aws_instance.frontend
> }
- moved = you renamed a block; tell Terraform it is the same resource, so it is not destroyed and recreated
> removed {
>   from = aws_s3_bucket.old
>   lifecycle { destroy = false }
> }
- removed … destroy = false = stop managing it, but leave the real bucket alone
These blocks go through plan and review like any other change.
? Recommended S3 locking today? | DynamoDB | *use_lockfile | No lock

# tf-mod | Variables, outputs, modules | Intermediate | Reuse without copying.
@ v doc 0 0 Variables
@ r folder 1 0 Root module
@ n box 2 0 network module
@ d box 2 1 app module
@ o card 3 0 Outputs
= Variables with validation
+ v r
~ v>r
> variable "env" {
>   type = string
>   validation {
>     condition     = contains(["dev", "prod"], var.env)
>     error_message = "env must be dev or prod."
>   }
> }
- type = string = the value must be text
- validation = checked during plan
- contains([...], var.env) = true if the value is in the list
A typo like `env = "prd"` now fails at plan time with a clear message, instead of creating resources with a wrong name.
= Modules
+ n d
~ r>n ;; r>d
> module "network" {
>   source  = "terraform-aws-modules/vpc/aws"
>   version = "~> 6.0"
>   name    = "shop-${var.env}"
>   cidr    = "10.0.0.0/16"
> }
> module "app" {
>   source    = "./modules/app"
>   vpc_id    = module.network.vpc_id
>   subnet_ids = module.network.private_subnets
> }
- source = registry address or local folder
- version = pinned version range (only for registry and Git sources)
- module.network.vpc_id = an output of the network module, passed as input to the app module
Terraform sees the reference and creates the network first.
= Outputs
+ o
~ n>o vpc_id ;; o>r
> output "load_balancer_dns" {
>   value       = module.app.lb_dns_name
>   description = "Public address of the shop"
> }
$ terraform output -raw load_balancer_dns
- output -raw = print only the value, handy in scripts
Outputs can also be read by other Terraform projects through the `terraform_remote_state` data source.
= for_each over count
* d
> resource "aws_s3_bucket" "team" {
>   for_each = toset(["payments", "search", "catalog"])
>   bucket   = "acme-${each.key}-data"
> }
- for_each = create one resource per item; addresses are `aws_s3_bucket.team["search"]`
- each.key = the current item
With `count = 3`, resources are numbered 0, 1, 2. Remove the middle one and the third shifts to index 1, so Terraform destroys and recreates it. With `for_each`, each keeps its own key.
= Data sources
* r
`data` blocks read things Terraform does not manage, for example the current AWS account or an existing network:
> data "aws_caller_identity" "me" {}
> output "account" { value = data.aws_caller_identity.me.account_id }
- aws_caller_identity = who you are logged in as, and in which account
? Why for_each over count? | Faster | *Stable keys | Cheaper

# tf-team | Teams, testing and drift | Advanced | Running it in a pipeline.
@ d laptop 0 0 Engineer
@ pr board 1 0 Pull request
@ ci gear 2 0 CI plan
@ pol shield 2 1 Policy
@ c cloud 3 0 Cloud
@ x user 3 1 Manual change
= Plan on every pull request
+ d pr ci
~ d>pr ;; ci>pr plan
An engineer opens a pull request that changes `.tf` files. CI runs `terraform plan` and posts the result as a comment. Reviewers read the **effect** ("1 to add, 0 to destroy") as well as the code. A surprising `-/+` on the database is caught before it happens.
= Automated checks
+ pol
~ ci>pol
$ terraform fmt -check -recursive
- fmt -check = fail if any file is not formatted; -recursive = include subfolders
$ terraform validate
- validate = syntax and references are correct
$ terraform test
- test = run `.tftest.hcl` files that plan or apply a module and assert results
$ trivy config .
- trivy config = scan for insecure settings, such as a public bucket or an open security group
**Policy as code** (OPA with Conftest, or HashiCorp Sentinel) enforces company rules on the plan: "no public buckets", "every resource has a Team tag".
= Apply after merge, with short-lived access
+ c
~ ci>c apply
After the pull request is approved and merged, CI applies the saved plan. CI gets temporary cloud credentials through **OIDC**, valid for one run. No person needs permanent admin keys on their laptop.
= Detect drift
+ x
~ !x>c console edit ;; ci>pr drift found
Someone changes a security group in the console during an incident. The cloud now **drifts** from the code. Schedule a nightly check:
$ terraform plan -detailed-exitcode
- -detailed-exitcode = exit code 0 means no changes, 1 means an error, 2 means changes exist
If it returns 2, the pipeline opens an issue or alerts the team, who either put the change into code or let Terraform revert it.
= Split the state | PRACTICE
* ci
One giant state for everything makes every plan slow and every mistake dangerous. Split by environment and by how often things change:
- `network/` (changes rarely);
- `data/` (databases, carefully);
- `apps/` (changes daily).
Each has its own state, its own pipeline and its own permissions. A mistake in an app change cannot touch the network.
? `plan -detailed-exitcode` returning 2 means... | error | no changes | *changes exist
