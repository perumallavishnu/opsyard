## Models and project scale
# project-scale | What project scale means | Beginner | Small, medium and large, and why the size changes the method.
@ s user 0 0 Small project
@ m team 1 0 Medium project
@ l team 2 0 Large project
@ r gauge 1 1 Risk
= Small | SCALE
+ s
" s Two of us, six weeks.
1 to 5 people, weeks to about 3 months, one component. A shop website, an internal form, a student project. Talking is enough to stay aligned.
= Medium | SCALE
+ m
" m Three teams' work must fit together.
About 5 to 20 people, 3 to 12 months, several components. A hospital booking system, a mobile banking app. You need written stories, reviews and planned releases.
= Large | SCALE
+ l
" l Forty suppliers, five years.
More than 20 people, a year or more, many teams and suppliers. An airline reservation system, a national tax platform. You need architecture, formal interfaces and coordination between teams.
= Size is not everything
+ r
~ s>r ;; m>r ;; l>r
A pacemaker program may be small, but a mistake can kill. **Risk**, **how stable the requirements are** and **how much the client is available** matter as much as size.
These numbers are rules of thumb. Companies draw the lines differently.
= Four questions before choosing
| Question | Points to |
| Are requirements fixed? | Waterfall, V-Model |
| Is failure dangerous? | V-Model, Spiral |
| Will needs change? | Scrum, Iterative |
| Does work arrive as requests? | Kanban |
? A 6-person pacemaker project should be chosen by... | size only | *risk as well as size | popularity

# waterfall | Waterfall model | Beginner | One pass through every phase, each signed off before the next.
@ c user 0 0 Client
@ ba user 1 0 Business analyst
@ d user 2 0 Designer
@ dev team 3 0 Dev team
@ qa user 4 0 Tester
= How it flows
+ c ba d
" c Here is everything I want.
w c>ba all needs
w ba>d signed document
The **Waterfall model** runs the phases of the SDLC once, strictly in order, like water falling down steps: it never flows back up. Each phase must be **finished, documented and signed off** before the next one starts.
| Phase | Who | What comes out |
| 1 Requirements | Client, business analyst | Software Requirements Specification (SRS), signed |
| 2 Design | Architect, designer | High-level and detailed design documents |
| 3 Implementation | Developers | The code for the whole system |
| 4 Testing | Testers | Test reports, defects fixed |
| 5 Deployment | Operations | The system installed for users |
| 6 Maintenance | Support and developers | Fixes and small changes |
The signed document from one phase is the input of the next. That is the **handover** you see in the scene.
= The long middle
+ dev qa
w d>dev spec
" dev Coding, months 4 to 9.
w dev>qa whole system
Developers build the **whole** system from the design documents, which can take many months. Only when all the code exists does testing begin.
- The client usually sees **nothing working** during this long middle; progress is reported as "percentage done" in a plan.
- Testers receive everything at once, so bugs pile up near the deadline, and testing time is often squeezed.
- Questions that come up during coding go back to the signed documents, not to a conversation with users.
= Where it breaks | PROBLEM
w qa>c month 12
" c This is not what I meant.
: c err first look
w !c>ba start again
The client sees the product for the first time in month 12, and it is not what they meant. A sentence in the requirements was understood differently by the analyst and the client. That misunderstanding from month 1 is found in month 12.
Going back means changing the requirements, then the design, then the code, then testing again: almost the whole project repeated. Studies of software projects have long shown that a defect found late costs many times more to fix than one found during requirements.
!! The cost of a mistake grows with the distance between making it and noticing it.
= Scale and fit | SCALE
: ba ok stable scope
| Point | Waterfall |
| Size | Small to medium, or one fixed part of a large programme |
| Requirements | Known and stable |
| Client | Mostly at start and end |
| Change | Expensive |
| Documents | Heavy |
= Real-time example | PRACTICE
" ba The tax rules are printed law.
w ba>d rules
w d>dev spec
w dev>qa build
A payroll module for a company of 300 staff. Six people, four months. The tax rules are published, the pay slip layout is fixed, the auditor wants signed documents. Nothing will change before April, so Waterfall is a calm choice.
= Good and bad
| Good | Bad |
| Simple to explain | Late feedback |
| Clear dates and documents | Testing squeezed at the end |
| Easy to audit | Poor with changing needs |
Winston Royce's 1970 paper, often cited as its origin, itself advised iterating.
? Best match for Waterfall? | A new social app | *Payroll with fixed tax rules | A research prototype

# v-model | V-Model | Beginner | Every design level has its own test level.
@ r doc 0 0 Requirements
@ a board 1 0 Architecture
@ m card 2 0 Module design
@ c laptop 3 1 Code
@ ut shield 2 2 Unit tests
@ it shield 1 2 Integration tests
@ at shield 0 2 Acceptance tests
= Down the left side
+ r a m c
~ r>a ;; a>m ;; m>c
The **V-Model** (verification and validation model) keeps Waterfall's order, but bends the line into a V. The left side goes **down** through more and more detailed design:
| Level (left side) | Describes | Written by |
| Requirements | What the users need | Analyst with the client |
| Architecture / system design | The main parts and how they connect | Architect |
| Module design | Each part in detail: functions, data | Senior developers |
At every level the team also asks: **how will we test this?** and writes that test plan immediately.
= Up the right side
+ ut it at
~ c>ut ;; ut>it ;; it>at
After coding at the bottom, testing climbs back **up** the right side, each level checking the design level opposite it:
- **Unit tests** check each module against its module design.
- **Integration tests** check that modules work together as the architecture says.
- **System tests** check the whole system.
- **Acceptance tests** check, with the client, that the requirements are met.
= The pairs
~ r>at verifies ;; a>it verifies ;; m>ut verifies
Tests are planned on the way **down**, so vague requirements are noticed early.
! Verification: did we build it right? Validation: did we build the right thing?
= Scale and fit | SCALE
| Point | V-Model |
| Size | Medium to large |
| Requirements | Clear, must be traceable |
| Risk | Safety or money critical |
| Testing | Planned from day one |
| Change | Expensive |
= Real-time example | PRACTICE
: r ok numbered
: at ok traced
~ r>at each one has a test
The brake control unit of a car. Twenty-five engineers, two years. Every requirement has a number, every number has a test, and an inspector can follow the line from one to the other. Automotive and medical standards expect this kind of traceability.
= Limits
Working software still appears late, and a change touches both sides of the V. Teams often run small V's inside each iteration.
? Acceptance tests verify... | module design | architecture | *requirements

# iterative | Iterative model | Beginner | Build a rough whole, then improve it round by round.
@ c user 0 0 Client
@ d team 1 0 Dev team
@ v1 small 2 0 Version 1
@ v2 cube 3 0 Version 2
@ v3 box 4 0 Version 3
= Rough first
+ c d v1
" d Here is a simple whole.
w d>v1 build
~ v1>c try
The **Iterative model** does not try to get everything right at once. It starts with a basic version of the **whole** product: plain screens, few rules, simple algorithms, but it works from start to finish.
Each **iteration** (round) is a small SDLC of its own: plan, design, build, test, review. The product is improved round after round, based on what was learned from the last version.
= Learn and refine
+ v2
" c Search must find misspelled names.
w c>d feedback
w d>v2 improve
The client and users try version 1 and give feedback: what is missing, what is confusing, what is too slow. The team plans the next round around the most important feedback, designs the change, builds it, tests it and shows version 2.
Because the whole product exists early, problems in the overall design are found in the first weeks, not at the end. The design must allow parts to be reworked, since early versions are deliberately simple.
= Closer each time
+ v3
w d>v3 improve
: v3 ok good enough
You stop when it is good enough, or when the next improvement is not worth its cost.
= Scale and fit | SCALE
| Point | Iterative |
| Size | Medium to large |
| Requirements | Main goal known, details open |
| Client | Looks at each version |
| Change | Normal |
| Risk | Design must allow rework |
= Real-time example | PRACTICE
" c Version 1 found half of them.
A search engine for a library of five million books. Twelve people, ten months. Version 1 matches exact titles, version 2 ranks results, version 3 handles spelling and several languages. Nobody could have specified good ranking in advance.
? Iterative builds first... | one finished part | *a rough whole | only documents

# incremental | Incremental model | Beginner | Deliver finished slices one after another.
@ c user 0 0 Client
@ d team 1 0 Dev team
@ a box 2 0 Login and catalogue
@ b box 3 0 Cart and payment
@ e box 4 0 Returns
= Slice by value
+ c d a
w d>a increment 1
~ a>c in use
The **Incremental model** splits the product into **increments**: slices that are each designed, built, tested and **released** completely, one after another.
- The overall requirements and architecture are planned at the start, so the slices fit together.
- Each increment is finished and usable on its own, not a rough draft.
- Users start using the first slice while later ones are being built.
= Add the next slice
+ b
w d>b increment 2
Later increments are added to what already runs. The most valuable ones come first.
= Compare with iterative
+ e
w d>e increment 3
**Incremental**: paint one finished corner of the picture at a time. **Iterative**: sketch the whole picture, then add detail. Agile does both.
= Scale and fit | SCALE
| Point | Incremental |
| Size | Small to large |
| Requirements | Core known, extras later |
| Client | Uses early parts |
| Money | Returns start early |
| Needs | Good architecture from the start |
= Real-time example | PRACTICE
" c We sold shoes in month 3.
An online shop for a shoe company. Eight people. Month 3: browse and order by phone. Month 5: card payment. Month 7: returns. The first increment earns money that helps pay for the next.
? Main benefit of increments? | No design needed | *Users get value early | No testing

# prototype | Prototype model | Beginner | Show something quickly to learn what is wanted.
@ c user 0 0 Client
@ d user 1 0 Designer
@ p card 2 0 Prototype
@ r doc 2 1 Requirements
@ dev team 1 1 Dev team
= I will know it when I see it | PROBLEM
+ c d
" c Make it friendly and modern.
" d What does that mean?
Some needs cannot be put into words.
= Show, do not ask | SOLUTION
+ p
w d>p sketch
~ p>c click
" c No, bigger buttons, fewer steps.
w d>p change
The **Prototype model** builds a quick, cheap model of the product, often just screens with no real logic behind them, and puts it in front of the client and users.
1. Gather rough requirements.
2. Build a prototype in days: paper sketches, a clickable Figma design, or a simple app.
3. Users try it and react: "no, bigger buttons, fewer steps".
4. Change the prototype and repeat until the client agrees.
Reacting to something real is much easier than describing a wish in words.
= Then build properly
+ r dev
~ p>r agreed ;; r>dev build
: r ok understood
**Throwaway** prototypes are only for learning. **Evolutionary** ones are improved until they become the product.
= Scale and fit | SCALE
| Point | Prototype |
| Size | Small to medium, or the screens of a large one |
| Requirements | Unclear, mostly about usage |
| Client | Must be available |
| Danger | Client believes it is finished |
= Real-time example | PRACTICE
" c Nurses wear gloves: no tiny icons.
A tablet app for nurses. Five people, three months. Paper sketches on Monday, a clickable Figma model on Thursday, tested on a real ward. The glove problem appeared on day four, not in month three.
!! Do not ship a throwaway prototype. It has no error handling, security or tests.
? A throwaway prototype is for... | production | *learning | performance

# spiral | Spiral model | Intermediate | Each round attacks the biggest risk.
@ g flag 0 0 Goals
@ r gauge 1 0 Risk analysis
@ b team 1 1 Build and test
@ p user 0 1 Plan and review
@ out box 2 0 Product
= One turn
+ g r b p
~ g>r ;; r>b ;; b>p ;; p>g
The **Spiral model**, described by Barry Boehm in 1986, repeats a loop. Each turn of the spiral has four quadrants:
| Quadrant | Activity |
| 1 Determine objectives | What should this round achieve, and what are the alternatives? |
| 2 Identify and resolve risks | What could make the project fail? Reduce it: prototypes, simulations, expert reviews |
| 3 Develop and test | Build and test the next level of the product |
| 4 Plan the next iteration | Review with the client and decide whether, and how, to continue |
The distance from the centre shows money spent so far; each turn costs more than the last.
= Risk decides
* r
" p Can it handle a million calls?
The team asks: what could kill this project? Then it spends this round on exactly that, often with a prototype.
= Growing turns
+ out
~ b>out
Early rounds are cheap: ideas and models. Later rounds cost more, when the big risks are gone.
= Scale and fit | SCALE
| Point | Spiral |
| Size | Large |
| Risk | High: new technology, big money |
| Requirements | Will change |
| Needs | People skilled in risk analysis |
| Small project | Too expensive |
= Real-time example | PRACTICE
" b Round 2: radar data at full speed.
A new air traffic control system. Two hundred people, six years. Round 1 proves the radar link, round 2 proves speed, round 3 runs beside the old system at one airport. Only then does the country switch.
? Spiral is driven by... | documents | *risk | speed

# rad | RAD model | Beginner | Rapid Application Development with users in the room.
@ u team 0 0 Users
@ t1 user 1 0 Developer A
@ t2 user 1 1 Developer B
@ tool gear 2 0 Low-code tool
@ app box 3 0 App
= The idea
+ u t1 t2
" u This field comes first.
w u>t1 workshop
w u>t2 workshop
**RAD** (Rapid Application Development), described by James Martin in 1991, puts speed first:
- **Requirements planning**: short workshops where users and developers agree on scope.
- **User design**: users and developers build and refine screens together, in repeated workshops (JAD: joint application design).
- **Construction**: small teams build parts in parallel with strong tools, reusing ready components.
- **Cutover**: testing, data conversion and switching to the new system.
The whole project is usually time-boxed to about 60 to 90 days.
= Build in parallel
+ tool
~ t1>tool ;; t2>tool
Parts are built at the same time from ready components.
= Join
+ app
~ tool>app combine
: app ok 70 days
Then the parts are joined and tested.
= Scale and fit | SCALE
| Point | RAD |
| Size | Small to medium; larger only if it splits into modules |
| Time | Very short |
| Users | Available almost daily |
| Technology | Known, with good tools |
| Poor for | High performance or risky technology |
= Real-time example | PRACTICE
" u We approved screens every Friday.
A leave approval app for a company of 2,000. Four developers with a low-code platform, two months. Staff from HR sat in every workshop.
? RAD needs... | a distant client | *users available often | six years

# xp-lean | XP, Lean and SAFe | Intermediate | Engineering habits, waste removal, and scaling to many teams.
@ p1 user 0 0 Developer A
@ p2 user 0 1 Developer B
@ tdd shield 1 0 TDD
@ ci gear 2 0 Continuous integration
@ t1 team 3 0 Team A
@ t2 team 3 1 Team B
@ art flag 4 0 Release train
= Extreme Programming
+ p1 p2 tdd ci
" p1 I type.
" p2 I check each line.
~ p1>tdd ;; tdd>ci
XP turns good engineering habits up: **pair programming**, **test-driven development**, **refactoring**, **continuous integration**, small releases.
= TDD: red, green, refactor
* tdd
: tdd err red
Write a failing test. Write the least code that passes. Clean up while tests protect you. Repeat every few minutes.
= Lean
* ci
Lean comes from Toyota. Remove **waste**: waiting, handoffs, unfinished work, defects, extra features. A **value stream map** records working and waiting time for each step. Waiting usually dominates.
= SAFe
+ t1 t2 art
" t1 We need your API by week 6.
" t2 Then we plan it together.
~ t1>art ;; t2>art
With ten teams on one product, plans must align. **SAFe** groups teams into an Agile Release Train that plans together for about 8 to 12 weeks. **LeSS** and **Nexus** are lighter ways to scale Scrum.
= Scale and fit | SCALE
| Method | Scale | Real-time example |
| XP | 2 to 12 people | Trading system with daily releases |
| Lean | Any | Cutting a 10-day approval to 1 day |
| LeSS, Nexus | 3 to 8 teams | One large web product |
| SAFe | 50 to 125 people per train, several trains | Bank with many linked products |
= Others you will meet
**Crystal** fits the process to team size. **FDD** plans by feature. **DSDM** fixes time and cost and flexes scope using MoSCoW: Must, Should, Could, Won't (this time).
? In TDD, what is written first? | The code | *A failing test | Documentation

# agile-scale | Agile models and their scale | Beginner | Scrum, Kanban and DevOps by project size.
@ s team 0 0 Scrum team
@ k board 1 0 Kanban board
@ d gear 2 0 DevOps pipeline
@ u team 2 1 Users
= Scrum | SCALE
+ s
" s Two-week goals, demo on Friday.
One team of up to 10, changing needs, months to years. **Example:** a food delivery app; six developers release a new feature every Sprint and watch what customers order.
= Kanban | SCALE
+ k
~ s>k requests
Any size, work that arrives unplanned. **Example:** the IT help desk of a university with 60 tickets a day. A Sprint plan would be wrong by noon.
= Scrumban | SCALE
* s k
A product team that also does support. **Example:** a payroll product: Sprint goal for new work, two people on the support lane with a WIP limit.
= DevOps | SCALE
+ d u
~ k>d ;; d>u several times a day
Underneath any of them, from 3 people to thousands. **Example:** a streaming service with hundreds of services; each small team builds, releases and runs its own.
= Mixed in one company
| Part of a bank | Model |
| Core accounting change | V-Model |
| Mobile app | Scrum |
| Operations desk | Kanban |
| All releases | DevOps pipeline |
One company rarely uses one model everywhere.
