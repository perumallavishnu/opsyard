## Architecture
# k8-why | Why Kubernetes | Beginner | Keeping many containers running on many machines.
@ o user 0 0 Operator
@ k gear 1 0 Kubernetes
@ n1 server 2 0 Node 1
@ n2 server 2 1 Node 2
@ n3 server 2 2 Node 3
= By hand | PROBLEM
" o Which node runs what?
+ o n1 n2 n3
~ o>n1 ssh ;; o>n2 ssh ;; !o>n3 forgot
Docker runs containers on one machine. A real product has fifty containers on ten machines. Someone must answer, all day:
- where should each container run, so no machine is overloaded?
- a machine died at 3 a.m.: which containers were on it, and where do they go now?
- how do we update to version 2 without downtime?
- traffic doubled: how do we add copies, and send users to them?
= Say what you want | SOLUTION
+ k
~ o>k 3 replicas
Kubernetes is **declarative**. Instead of commands ("start a container on node 2"), you describe the result:
> replicas: 3
> image: acme/web:1.4.0
Kubernetes stores this **desired state** and works continuously to make reality match it.
= It places work
~ k>n1 ;; k>n2 ;; k>n3
: n1 ok running
: n2 ok running
: n3 ok running
The **scheduler** looks at how much CPU and memory each copy asks for, and how much is free on each node, and places the three copies on different nodes so that one failure does not take all of them.
= It heals
: n2 err down
~ k>n3 replace
Node 2 dies. Kubernetes notices that only two copies are running while three are wanted, and starts a replacement on another node, without anyone waking up.
This loop, **observe, compare with the desired state, act**, runs for everything in the cluster. It is the whole idea of Kubernetes.
= What it adds
| Feature | Without Kubernetes | With Kubernetes |
| Placement | Choose machines by hand | Scheduler picks nodes |
| Failures | Restart by hand | Replaced automatically |
| Finding services | Hard-coded IP addresses | Stable names (Services, DNS) |
| Updates | Downtime or careful scripts | Rolling updates and rollback |
| Scaling | Add machines and configure | Change one number, or autoscale |
= When not to use it | PRACTICE
Kubernetes has a real cost: it must be learned, upgraded, secured and monitored. For one small service, a managed platform (Cloud Run, App Runner, Heroku-like services) or a single server with Docker Compose is often the better choice. Kubernetes pays off with many services, several teams, or strict uptime needs.

= The API server
+ cp api
The **kube-apiserver** is the front door. Every request, from kubectl, from controllers, even from nodes, goes through it. For each request it checks:
- **authentication**: who are you? (a certificate, a token, your cloud login);
- **authorisation**: may you do this? (RBAC rules);
- **admission**: does the object follow the cluster's policies? Admission can also add defaults.
$ kubectl cluster-info
- cluster-info = show the API server's address
= etcd
+ etcd
~ api>etcd store
**etcd** is a small, very reliable key-value database that holds the entire cluster state: every object, every setting. Only the API server talks to it.
If etcd is lost without a backup, the cluster forgets everything it was running. Managed clusters (EKS, GKE, AKS) back it up for you; self-managed clusters must do it themselves:
$ etcdctl snapshot save /backup/etcd-$(date +%F).db
- etcdctl snapshot save = write a consistent copy of etcd's data to a file
= The scheduler
+ sch
~ sch>api pick a node
The **kube-scheduler** watches for new Pods that have no node yet. For each one it:
- **filters** out nodes that cannot run it (not enough free CPU or memory, wrong labels, taints);
- **scores** the rest (spread across zones, keep images close, balance load);
- writes the chosen node back to the API server.
It only decides; it does not start anything.
= Controllers
+ cm
~ cm>api reconcile
The **kube-controller-manager** runs many small loops called **controllers**, each responsible for one kind of object:
- the Deployment controller creates ReplicaSets;
- the ReplicaSet controller creates or deletes Pods to match the count;
- the Node controller notices dead nodes;
- the Job controller tracks finished tasks.
Each one compares actual with desired state and acts on the difference.
= The node
+ nd kl cri pod
~ api>kl pod spec ;; kl>cri start ;; cri>pod
On each worker node, the **kubelet** asks the API server "which Pods are mine?", then tells the **container runtime** (containerd or CRI-O) to pull images and start containers. It runs health checks and reports status back.
$ kubectl get pods -A -o wide
- -A = all namespaces; -o wide = includes the NODE column, showing where each Pod runs
= Networking on the node
+ kp
~ kp>pod route
**kube-proxy** programs the node's network rules so that traffic to a Service's virtual address reaches one of its Pods. Some network plugins (such as Cilium) replace it with faster eBPF programs.
The **CNI plugin** (Calico, Cilium, Flannel, or the cloud's own) gives every Pod an IP address and connects Pods across nodes.

# k8-pod | Pods and probes | Beginner | The smallest unit, and how it reports health.
Z pz 1 0 2 2 Pod
@ k gear 0 0 kubelet
@ i small 1 1 Init container
@ a box 1 0 App
@ s box 2 0 Sidecar
@ v bucket 2 1 Shared volume
= One Pod
+ pz a
A **Pod** is one or more containers that always run together on one node, share one IP address and can share volumes. Most Pods have a single main container.
$ kubectl run web --image=nginx:1.28 --port=80
- run web = create a single Pod named web (fine for experiments; real apps use Deployments)
- --image = the image; --port = the container port
= Sidecars
+ s v
~ a>v logs ;; v>s read
A **sidecar** is a helper container in the same Pod: a log shipper, a proxy, a certificate refresher. It shares the Pod's network (`localhost`) and volumes with the main container.
= Init containers
+ i
~ i>a then
**Init containers** run one after another, to completion, **before** the main containers start: wait for the database, run a migration, download configuration.
> initContainers:
> - name: wait-db
>   image: busybox
>   command: ["sh", "-c", "until nc -z db 5432; do sleep 2; done"]
- command = loop until port 5432 on host `db` answers, checking every 2 seconds
An init container with `restartPolicy: Always` becomes a **native sidecar**: it starts first and keeps running.
= Liveness probe
+ k
~ !k>a liveness
: a warn restarting
The kubelet can check a container's health in three ways: an HTTP request, a TCP connection, or a command. A **liveness probe** answers "is it stuck?". If it fails several times, the kubelet **restarts** the container.
> livenessProbe:
>   httpGet: { path: /healthz, port: 8080 }
>   periodSeconds: 10
>   failureThreshold: 3
- httpGet = call this URL; any status 200–399 counts as healthy
- periodSeconds: 10 = check every 10 seconds
- failureThreshold: 3 = restart after 3 failures in a row
!! Keep liveness checks simple. If a liveness check calls the database and the database is slow, every Pod restarts at once and makes things worse.
= Readiness and startup probes
~ k>a readiness
: a ok Ready
- A **readiness probe** answers "may it receive traffic?". If it fails, the Pod is taken out of its Services, but **not** restarted. Use it while warming caches or when a dependency is down.
- A **startup probe** gives slow-starting apps time. Liveness and readiness checks wait until it succeeds.
> readinessProbe:
>   httpGet: { path: /ready, port: 8080 }
> startupProbe:
>   httpGet: { path: /healthz, port: 8080 }
>   failureThreshold: 30
>   periodSeconds: 5
- startupProbe with 30 × 5 seconds = the app gets up to 150 seconds to start
= Pods are temporary | PRACTICE
* pz
A Pod created directly (a "bare" Pod) is not replaced if its node fails. It is simply gone. Always run real applications through a controller, usually a **Deployment**, which replaces Pods automatically.

# k8-deploy | Deployments and rollouts | Beginner | Replicas, updates and rollback.
@ d board 0 0 Deployment
@ r1 folder 1 0 ReplicaSet v1

@ a pod 2 0 v1

= Replicas
+ d r1 a b
~ d>r1 ;; r1>a ;; r1>b
A Deployment manages a ReplicaSet, which manages Pods.
> apiVersion: apps/v1
> kind: Deployment
> metadata: { name: web }
> spec:
>   replicas: 2
>   selector: { matchLabels: { app: web } }
>   template:
>     metadata: { labels: { app: web } }
>     spec:
>       containers: [{ name: web, image: "acme/web:1.0" }]
- replicas: 2 = how many Pods
- selector.matchLabels = which Pods count as "mine"
- template = the blueprint for new Pods; its labels must match the selector
$ kubectl apply -f web.yaml
$ kubectl get deploy,rs,pods -l app=web
- get deploy,rs,pods = show all three levels at once
= Heal
: b err deleted
~ r1>b new Pod
$ kubectl delete pod web-7d4b9c-x2k8p
- delete pod = remove one Pod, as a node failure would
The ReplicaSet counts Pods with the label `app=web`, sees one instead of two, and creates a new one within seconds. Labels are what connect the levels.
= Update
+ r2 c
~ d>r2 ;; r2>c
$ kubectl set image deployment/web web=acme/web:2.0
- set image deployment/web = change the Deployment's Pod template
- web=acme/web:2.0 = container name `web` gets image `acme/web:2.0`
Changing the template makes the Deployment create a **new** ReplicaSet for version 2. The new one grows while the old one shrinks. Two settings control the pace:
> strategy:
>   rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
- maxSurge: 1 = at most one extra Pod above `replicas` during the update
- maxUnavailable: 0 = never fewer ready Pods than `replicas`
= Finish
+ e
x a b
~ r2>e
: c ok Ready
: e ok Ready
An old Pod is removed only after a new Pod is **Ready**. Users always reach working Pods. When all new Pods are ready, the old ReplicaSet is scaled to zero but kept, for rollback.
$ kubectl rollout status deployment/web
- rollout status = wait until the rollout completes, or report that it is stuck
= Roll back
~ d>r1 undo
$ kubectl rollout undo deployment/web
- rollout undo = scale the previous ReplicaSet back up and the current one down
$ kubectl rollout history deployment/web
- rollout history = the revisions you can return to
$ kubectl annotate deployment/web kubernetes.io/change-cause="Release 2.0"
- annotate … change-cause = a note shown in the history, so you know what each revision was
With GitOps, revert the commit instead, so Git stays the source of truth.

# k8-other | StatefulSet, DaemonSet, Job, CronJob | Intermediate | Workloads beyond stateless web servers.
@ ss board 0 0 StatefulSet
@ p0 db 1 0 db-0
@ p1 db 2 0 db-1
@ ds board 0 1 DaemonSet
@ n1 pod 1 1 Node 1 agent
@ n2 pod 2 1 Node 2 agent
@ j board 0 2 Job

= StatefulSet
+ ss p0 p1
~ ss>p0 first ;; ss>p1 then
Deployment Pods are interchangeable, with random names. Databases and message queues need more:
- **stable names**: `db-0`, `db-1`, `db-2`, always the same;
- **stable storage**: each Pod gets its own disk, which follows it;
- **ordered** start and stop: `db-0` first, then `db-1`.
A **StatefulSet** provides exactly that, together with a **headless Service** that gives each Pod its own DNS name, such as `db-0.db.shop.svc.cluster.local`.
= Storage follows the Pod
: p0 ok disk 0
: p1 ok disk 1
> volumeClaimTemplates:
> - metadata: { name: data }
>   spec:
>     accessModes: [ReadWriteOnce]
>     resources: { requests: { storage: 50Gi } }
- volumeClaimTemplates = create one PVC per Pod: `data-db-0`, `data-db-1`
If `db-1` is rescheduled to another node, it gets `data-db-1` back. Note: Kubernetes does **not** copy data between replicas; the database itself must replicate. Operators (see the last lesson) handle that.
= DaemonSet
+ ds n1 n2
~ ds>n1 ;; ds>n2
A **DaemonSet** runs exactly one Pod on every node (or every node matching a selector). When a node joins, it gets one automatically.
Typical uses: log collectors (Fluent Bit), node monitoring (node-exporter), network and storage plugins.
$ kubectl get daemonsets -A
- get daemonsets -A = see which DaemonSets run in all namespaces, and on how many nodes
= Job
+ j c
~ j>c run
: c ok Completed
A **Job** runs Pods until a task **completes**, retrying on failure: a database migration, a report, a data import.
$ kubectl create job migrate --image=acme/web:2.0 -- npm run migrate
- create job migrate = a one-off Job named migrate
- -- npm run migrate = the command to run in the container
> spec:
>   backoffLimit: 3
>   activeDeadlineSeconds: 600
- backoffLimit: 3 = retry at most 3 times
- activeDeadlineSeconds: 600 = give up after 10 minutes
= CronJob
~ j>c 02:00
A **CronJob** creates a Job on a schedule, written like cron:
> schedule: "0 2 * * *"
> timeZone: "Asia/Kolkata"
> concurrencyPolicy: Forbid
- schedule: "0 2 * * *" = every day at 02:00
- timeZone = in this time zone instead of the cluster's
- concurrencyPolicy: Forbid = do not start a new run while the previous one is still going
A schedule can occasionally run twice or be skipped, so make the task safe to run twice (**idempotent**).

- --port=80 = the Service's port
- --target-port=8080 = the container's port

| Another namespace | `web.shop` |

* s

# k8-gw | Ingress, Gateway API and NetworkPolicy | Intermediate | Getting traffic in, and keeping it out.

= Ingress
+ u g w
~ u>g ;; g>w
An **Ingress** object maps host names and paths to Services, and an **Ingress controller** does the actual proxying:
> rules:
> - host: shop.example.com
>   http:
>     paths:
>     - path: /
>       pathType: Prefix
>       backend: { service: { name: web, port: { number: 80 } } }
- host = which domain
- path / with pathType Prefix = every path starting with `/`
- backend.service = which Service and port receives the request
The Ingress API still works, but it is **frozen**: no new features.
= What changed in 2026
* g
: g warn migrate
The widely used **Ingress NGINX** controller was retired in March 2026: no more releases or security fixes. Kubernetes recommends moving to **Gateway API**; the **ingress2gateway** tool converts existing Ingress objects.
$ kubectl get pods -A -l app.kubernetes.io/name=ingress-nginx
- -l app.kubernetes.io/name=ingress-nginx = find out whether your cluster still runs it
= Gateway API
+ r a
~ u>g ;; g>r ;; r>w / ;; r>a /api
Gateway API splits the job between roles:
- **GatewayClass**: which controller implements gateways (set up once by the platform team);
- **Gateway**: the entrance itself, with its listeners, ports and TLS certificates (owned by the platform team);
- **HTTPRoute**: routing rules for one app (owned by the app team), attached to a Gateway.
> kind: Gateway
> spec:
>   gatewayClassName: envoy
>   listeners:
>   - name: https
>     port: 443
>     protocol: HTTPS
>     tls: { certificateRefs: [{ name: shop-tls }] }
- gatewayClassName = which implementation runs this Gateway
- listeners = what it accepts: HTTPS on port 443 using the certificate in Secret `shop-tls`
= Traffic splitting
~ r>w 90% ;; r>a 10%
Canary releases are part of the standard:
>     backendRefs:
>     - { name: web-v1, port: 80, weight: 90 }
>     - { name: web-v2, port: 80, weight: 10 }
- weight = share of requests: 90% to v1, 10% to v2
Header matches ("send testers with header `x-beta: 1` to v2") and redirects are built in too.
= Open by default | RISK
+ d
~ !w>d
By default every Pod can connect to every other Pod in the cluster. If the web front is compromised, the attacker can reach the database directly.
= NetworkPolicy
* d
: d ok api only
~ a>d
A **NetworkPolicy** limits which Pods may talk to which. Start by denying everything in a namespace, then allow only what is needed:
> kind: NetworkPolicy
> metadata: { name: db-from-api }
> spec:
>   podSelector: { matchLabels: { app: db } }
>   ingress:
>   - from: [{ podSelector: { matchLabels: { app: api } } }]
>     ports: [{ port: 5432 }]
- podSelector (top) = the Pods this policy protects: the database
- ingress.from = who may connect in: only Pods labelled `app: api`
- ports = and only on port 5432
!! Your network plugin must support NetworkPolicy (Calico and Cilium do). Without support, policies are silently ignored.

# k8-conf | ConfigMaps, Secrets and volumes | Intermediate | Settings and data for Pods.

= ConfigMap
+ cm p
~ cm>p env or file
A **ConfigMap** holds non-secret settings. A Pod receives them as environment variables or as files:
> envFrom:
> - configMapRef: { name: web-config }
> volumeMounts:
> - { name: cfg, mountPath: /etc/web }
- envFrom.configMapRef = every key becomes an environment variable
- volumeMounts … /etc/web = every key becomes a file in that folder (with a matching `volumes` entry)
Mounted files are updated automatically after a short delay; environment variables are read only when the container starts, so they need a restart:
$ kubectl rollout restart deployment/web
- rollout restart = replace all Pods gradually, so they read the new values
= Secret
+ se
~ se>p
A **Secret** works the same way for passwords, tokens and certificates. But **base64 is encoding, not encryption**: anyone who can read the Secret object can decode it.
Protect Secrets by:
- turning on **encryption at rest** for etcd;
- giving very few people and ServiceAccounts `get` on Secrets;
- or keeping the real values in Vault or a cloud secret manager and syncing them with **External Secrets Operator**.
= Ask for storage
+ pvc
~ p>pvc 10Gi
A Pod that needs a disk asks for it with a **PersistentVolumeClaim** (PVC): size, access mode and storage class. The Pod refers to the claim by name and does not need to know what kind of disk it gets.
= Get storage
+ pv sc
~ pvc>sc ;; sc>pv create ;; pv>pvc bound
The claim names a **StorageClass**. Its **CSI driver** (Container Storage Interface: the plug-in for a cloud or storage system) creates a real disk, represents it as a **PersistentVolume** (PV), and **binds** it to the claim. When the Pod starts on a node, the disk is attached there.
$ kubectl get pvc
- get pvc = STATUS should be `Bound`; `Pending` means no disk was created yet
= Reclaim policy and access modes | RISK
: pv warn Delete
The **reclaim policy** decides what happens to the disk when its claim is deleted:
- `Delete` (default for most cloud classes): the disk and its data are deleted;
- `Retain`: the disk is kept for manual recovery.
| Access mode | Means |
| ReadWriteOnce | One node may mount it read-write |
| ReadWriteOncePod | Only one Pod may mount it |
| ReadOnlyMany | Many nodes, read-only |
| ReadWriteMany | Many nodes read-write; needs shared storage such as NFS or EFS |

= Requests and limits
+ d a n1
~ d>a ;; a>n1
> resources:
>   requests: { cpu: 250m, memory: 256Mi }
>   limits:   { memory: 512Mi }
- requests.cpu: 250m = reserve a quarter of a CPU core (`m` = thousandths). The scheduler places Pods by requests
- requests.memory: 256Mi = reserve 256 MiB
- limits.memory: 512Mi = never more than 512 MiB
Going over the **CPU** limit only slows the container down (throttling). Going over the **memory** limit gets it killed: status **OOMKilled**, then restarted. Many teams set a memory limit but no CPU limit, to avoid needless throttling.
= Quality of service classes
* a
Kubernetes ranks Pods for eviction when a node runs out of memory:
| Class | When | Evicted |
| Guaranteed | Requests equal limits for every container | Last |
| Burstable | Some requests set | In between |
| BestEffort | No requests or limits at all | First |
$ kubectl top pods
- top pods = actual CPU and memory use, to choose sensible requests
= Placement rules
* n1
- **nodeSelector**: run only on nodes with a label, such as `disktype: ssd`.
- **Affinity / anti-affinity**: prefer or require being near (or away from) other Pods; for example, never two replicas on one node.
- **Taints and tolerations**: a tainted node repels Pods unless they **tolerate** the taint; used for GPU nodes or dedicated nodes.
- **Topology spread constraints**: spread replicas evenly across zones.
$ kubectl taint nodes gpu-1 gpu=true:NoSchedule
- taint … gpu=true:NoSchedule = only Pods tolerating `gpu=true` may be scheduled on gpu-1
= Scale Pods automatically
+ h b
~ h>d more ;; d>b
$ kubectl autoscale deployment web --min=2 --max=10 --cpu=70%
- autoscale deployment web = create a HorizontalPodAutoscaler for it
- --min=2 --max=10 = never fewer than 2 or more than 10 replicas
- --cpu=70% = add replicas when average CPU use goes above 70% of requests
The **HorizontalPodAutoscaler** (HPA) needs metrics-server. The **Vertical Pod Autoscaler** adjusts requests instead; **KEDA** scales on events such as queue length, even down to zero.
= Scale nodes automatically
+ n2
~ b>n2

When new Pods stay Pending because no node has room, **Cluster Autoscaler** or **Karpenter** adds a node from the cloud, and removes nodes that stay nearly empty.
= Planned disruption
* b

- minAvailable: 2 = a drain waits rather than leave fewer than 2 web Pods running

= Role: what is allowed
+ r api
**RBAC** (role-based access control) decides who may do what. A **Role** lists allowed **verbs** on **resources** in one namespace:
> kind: Role
> metadata: { name: pod-reader, namespace: shop }
> rules:
> - apiGroups: [""]
>   resources: [pods, pods/log]
>   verbs: [get, list, watch]
- apiGroups: [""] = the core API group, where Pods live
- resources = which kinds of objects
- verbs = which actions: get, list, watch, create, update, patch, delete
A **ClusterRole** does the same cluster-wide, or as a reusable template.
= RoleBinding: who gets it
+ u rb
~ u>rb ;; rb>r ;; r>api allowed
$ kubectl create rolebinding ana-reads --role=pod-reader --user=ana -n shop
- create rolebinding ana-reads = grant a Role
- --role=pod-reader = which Role
- --user=ana = to whom; `--group` or `--serviceaccount=shop:web` also work
RBAC only **adds** permissions; there is no "deny" rule. Anything not granted is refused.
$ kubectl auth can-i delete pods --as ana -n shop
- auth can-i = ask "may this user do this?"; answers yes or no
- --as ana = check for another user (needs permission to impersonate)
= ServiceAccounts
+ sa p
~ p>sa token ;; sa>rb
Programs inside Pods also call the API, as a **ServiceAccount**. Every namespace has a `default` one. Give each app its own ServiceAccount with only the permissions it needs. If the app never calls the Kubernetes API, do not give it a token at all:
> spec:
>   serviceAccountName: web
>   automountServiceAccountToken: false
= Pod Security Standards
* p
: p ok restricted
Pod Security Admission enforces one of three standard levels per namespace, using labels:
$ kubectl label namespace shop pod-security.kubernetes.io/enforce=restricted
- label namespace shop … enforce=restricted = refuse Pods in shop that break the "restricted" rules
| Level | Allows |
| privileged | Anything |
| baseline | Blocks the most dangerous settings, such as host networking or privileged containers |
| restricted | Also requires non-root, no privilege escalation, dropped capabilities, a seccomp profile |
= User namespaces
With **user namespaces** (`hostUsers: false` in the Pod spec), root inside the container maps to an unprivileged user on the node. A container escape then lands as a nobody. Generally available since Kubernetes v1.36 on Linux.
= Admission policies
~ api>p admission
**ValidatingAdmissionPolicy** lets you write rules in the CEL language, checked by the API server itself, no webhook needed: "every Deployment must set resource requests". **Kyverno** and **OPA Gatekeeper** go further, for example "only images signed by our pipeline".
!! Giving `cluster-admin` to a CI job or an application is the most common serious mistake. If that token leaks, the whole cluster is lost.

= Repetition | PROBLEM
+ c k
An app needs a Deployment, Service, ConfigMap, HTTPRoute, HPA and more: twelve YAML files. Three environments (dev, staging, prod) differ in only a few values. Copying the files three times means the copies slowly drift apart.
= Helm
+ h v
~ c>h templates ;; v>h values ;; h>k release
**Helm** is the package manager for Kubernetes. A **chart** is a folder of YAML templates with placeholders, plus a `values.yaml` file of defaults. An installed chart is a **release**.
$ helm repo add bitnami https://charts.bitnami.com/bitnami
- repo add = remember a chart repository under a short name
$ helm install shop ./chart -f prod.yaml -n shop --create-namespace
- install shop = install a release named `shop`
- ./chart = from this local chart folder (or `bitnami/postgresql` from a repository)
- -f prod.yaml = override default values with this file
- -n shop --create-namespace = into namespace shop, creating it if needed
$ helm upgrade shop ./chart -f prod.yaml
- upgrade = apply a new chart version or new values; Helm keeps each as a revision
$ helm rollback shop 1
- rollback shop 1 = return the release to revision 1
$ helm template shop ./chart -f prod.yaml
- template = print the final YAML without installing, to review it
= Helm 4
* h
Helm 4 (November 2025) uses Kubernetes **server-side apply** for new installs, so conflicts with other tools changing the same objects are detected. Existing releases keep their earlier method unless you change it.
= Kustomize
* v
**Kustomize** takes a different approach: no templates. You keep plain YAML in a `base/` folder and small patches in `overlays/dev`, `overlays/prod`:
> # overlays/prod/kustomization.yaml
> resources: [../../base]
> replicas: [{ name: web, count: 5 }]
> images: [{ name: acme/web, newTag: "1.8.2" }]
- resources = start from the base
- replicas / images = change only these values for production
$ kubectl apply -k overlays/prod
- -k = build with Kustomize (built into kubectl) and apply
= Operators
+ o d
~ k>o custom resource ;; o>d manage
Running a database well needs expert knowledge: backups, failover, upgrades. An **operator** puts that knowledge into code.
- A **CRD** (custom resource definition) adds a new kind of object, such as `PostgresCluster`.
- The **operator** is a controller that watches those objects and does the work: creates the StatefulSet, configures replication, takes backups, promotes a new primary when one fails.
> kind: Cluster
> apiVersion: postgresql.cnpg.io/v1
> spec:
>   instances: 3
>   storage: { size: 50Gi }
- instances: 3 = the CloudNativePG operator runs a primary and two replicas, with automatic failover
