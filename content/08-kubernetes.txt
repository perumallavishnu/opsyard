# k8-why | Why Kubernetes | Beginner | Keeping many containers running on many machines.
@ o user 0 0 Operator
@ k gear 1 0 Kubernetes

= By hand | PROBLEM
" o Which node runs what?
+ o n1 n2 n3
~ o>n1 ssh ;; o>n2 ssh ;; !o>n3 forgot
Fifty containers on ten machines: where does each run, what if a machine dies, how do you update without downtime?
= Say what you want | SOLUTION
+ k
~ o>k 3 replicas
Kubernetes is **declarative**: you describe the desired state and it works to make it true.
= It places work
The scheduler looks at requested CPU and memory on each node and spreads the three copies across them.
~ k>n1 ;; k>n2 ;; k>n3
: n1 ok running
: n2 ok running
: n3 ok running
= It heals
: n2 err down
~ k>n3 replace
A node dies. The actual state no longer matches, so Kubernetes starts a replacement elsewhere.
That loop, **observe, compare, act**, is the whole idea.
= What it adds
Scheduling, self-healing, service discovery, load balancing, rolling updates, scaling, configuration, storage.
= When not to | PRACTICE
A single small service may be better on a managed platform or one server with Compose. Kubernetes has a real operating cost.

A new ReplicaSet grows as the old shrinks. `maxSurge` and `maxUnavailable` set the pace.

= Requests and limits
